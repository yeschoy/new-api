# 邀请充值返现运维说明

## 上线顺序

1. 先部署数据库迁移和后端，确认 `cashback_order_contexts`、`cashback_rewards`、`cashback_device_links`、`cashback_quota_mutations`、`cashback_campaigns`、`epay_payment_evidences`、`admin_quota_credit_evidences`、`wallet_refund_credit_events` 已创建。所有写入实例升级并核对旧实例/历史余额前，不启用退款参考金额环境开关。
2. 保持充值人、邀请人两个返现方向均关闭；不存在第三种“被邀请人返现”。
3. 在系统设置的 **Billing & Payment → Referral Cashback** 中配置单笔及 24 小时额度上限、T+N、风险阈值及仅充值人的四档审核策略。免审主开关默认关闭；开启后低/中默认自动批准，高/严重默认人工审核，邀请人始终人工审核。
4. 确认支付合规声明后，按需启用方向；充值人返现还须由 Root 明确创建有期限、每人正额次数上限的独立活动。不会迁移生成历史活动；邀请人方向不受充值人活动/次数限制。
5. 使用新建在线充值订单分别验证无邀请人充值奖励、有邀请人两方向、支付在活动结束后的独立邀请人奖励、自动批准立即发放开/关、人工审核 T+N、幂等与审计。新订单始终保存订单上下文；首次启用前上下文会标记为不合格，充值仍正常到账且不会补发。

## 结算与停用

- 邀请人和需要人工审核的充值人奖励仍需审核通过、达到 `支付成功时间 + N×24 小时` 且没有当前硬阻断，才会由 `cashback_settlement` 发放。自动批准的充值人奖励可选择仍等 T+N，或在已验签支付的同一资金事务中立即发放（该开关默认开启）；支付、欠额、额度 fence、对账及幂等校验都不能跳过。
- 关闭方向开关只停止后续支付成功订单的新计提；充值人活动可提前结束，但不修改已有奖励的快照和审核/结算状态。
- 如需紧急停止新计提，请关闭两个方向。不要删除返现记录或直接改写用户额度。
- 系统任务失败、对账异常、开放欠额及高风险聚集可在 `/cashback` 管理页查看。
- 发放、奖励追回和本金追回会在主数据库事务内写入 `cashback_quota_mutations`。结算前对账以该表为资金证据；独立 `LOG_DB` 中的人类审计日志仅为尽力记录。
- 对账每次只按主键顺序检查固定批次的奖励、订单上下文和资金证据，不在每次发放前扫描完整历史。发现问题的批次会停留并阻止继续结算；管理页的对账问题数表示当前检查批次，而非全历史总数。
- Redis 开启时，返现资金事务会短暂建立用户额度 fence。fence 期间认证/资料读取可直接读取数据库且不会发布缓存，但额度查询、计费信任旁路、预扣和缓存发布均保持失败关闭；事务结束后缓存保持短暂不可用，再从已提交数据库余额重新水合。提交后的认证版本发布与会话撤销不会因额度缓存刷新延期而跳过。
- 只要用户额度存在排队中或已交换到执行中的批量增量，无论 Redis 用户哈希是否存在，数据库余额都不视为可追回权威值；异常处置会在任何账务修改前失败，等待批量额度落库后再重试。fence 所有权丢失时会删除受影响的余额哈希，但不会删除新 owner 的 fence。

## 退款、拒付和争议

首期**不接入支付渠道的自动退款、拒付或争议回调**。管理员必须在 `/cashback` 的返现详情中逐笔执行“记录支付异常”，并填写理由及可选凭证引用。

异常处置顺序固定为：

1. 取消尚未发放的双方返现，或从双方主额度追回已发放返现；
2. 再按累计退款比例冲正充值用户的原实际到账额度；
3. 余额不足部分分别记录为返现欠额或本金欠额，并阻断相关账号后续返现；
4. 欠额只能通过独立的管理员处置操作解决，解决不会恢复已取消奖励。

任何部分退款都会撤销该订单的全部返现，但充值本金只按累计退款比例冲正。管理员提交的是 0–10000 基点的**累计比例**；比例只能单调增加，重复提交同一异常和比例不会再次扣减。

## 只读退款参考与会计边界

返现发放后直接混入 `quota`，系统不在日常消费时跟踪逐笔资金来源。新入账在 `wallet_refund_credit_events` 中按钱包实际到账顺序记录：在线/人工补单购买、管理员 add 可退购买批次，实际发放赠送与额度码/签到/转入等不可退批次；旧余额只作为不可退款开口。管理员减额、覆盖或来源指定追回会使该用户数字参考转人工，不能用历史消费日志补造额度来源。异常处理仍采用“先取消/追回返现，再冲正本金”的确定性会计约定，不应解释为恢复了真实历史消费来源。

`/cashback` 的管理员报表按已记录消费日志展示充值区间，但这些日志可缺失、包含套餐消费，只是参考。最终 FIFO 剩余与日志独立，使用**全部有序入账与最终主库钱包余额**；管理员查询前须暂停该用户的新使用并确认预扣、异步退还和批量余额已结清，系统不自动证明这点。部署开关 `CASHBACK_REFUND_REFERENCE_ENABLED` 默认关闭：先确认所有钱包写入实例已升级、异常/旧余额及已线下退款记录已人工核对，才可将其设置为 `true`，否则报表只给已记录消费与人工核对提示。跨表来源时间不能替代入账事件 ID 的顺序，旧历史不会回填为可退。

管理员可在查询时逐单确认易支付商户**实际收款为 CNY**，此后该次查询才按验签金额和未消费购买额度比例给出手工退款参考。易支付签名本身不证明币种；管理员 add 金额是其原始 CNY 输入声明，不是支付凭据。没有签名金额、币种未确认、其他渠道或缺少完整来源时，不显示貌似准确的现金总额；部分有凭据订单可显示逐笔参考，但不可当作完整总额。本报表不会执行退款、扣钱包、追返现或防止管理员线下重复给付，实际资金处置始终由管理员负责。

## 审计与隐私

配置修改、审核、异常处置、欠额解决以及完整 IP/设备详情读取均写入管理员审计日志。浏览器在登录、注册和在线充值下单时通过 `X-Device-Signal` 发送版本化信号；服务端只保存二次散列，且该信号只能作为关联风险证据。设备信号缺失或非法时，服务端使用仅限该用户的隔离锚点保留首次/最近 IP，该锚点不参与“同设备多账号”统计。缺失设备信号不会阻断正常充值，单一 IP 或设备命中也不会自动拒绝。
