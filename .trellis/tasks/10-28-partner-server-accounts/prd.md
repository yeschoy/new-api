# 合作方服务端密钥接入：子账号首次使用自动开户

## Goal

让合作方（首个为可得财务，测试站 `test.cw.mercuryseek.cn`）把野菜API当作内置的模型服务商接入：合作方后端持服务端密钥，为它的每个用户在野菜自动开一个子账号、领取长期有效的模型 API Key、查询额度并完成充值。终端用户全程不需要登录或授权野菜账号，付款在合作方界面内完成。

参照模式：AdsPower 内嵌 FlashIP，用户无需登录服务商账号。

## Background

- 现有 Partner OAuth（授权码 + PKCE，`.trellis/spec/backend/partner-oauth.md`）已上线。绑定、刷新令牌和 Key 30 天硬截止，刷新不延长。可得的日报机器人、工单自动回复等后台任务要长期运行，不适合这种方式。
- 可得测试站目前在自己页面上收集野菜账号密码，并嵌入人机验证（截图，2026-10-28）。这会让第三方接触用户密码明文并绕过 2FA/Passkey，不符合 OWASP。本任务上线后，可得必须删除该表单（见“外部依赖”）。

## Key Decisions（用户已确认）

| # | 决策 | 结论 |
|---|---|---|
| D1 | 接入形态 | 服务端密钥直连，用户无需在野菜登录或授权；与现有 Partner OAuth 并存，后者行为不变 |
| D2 | 账号模型 | 每个合作方用户对应一个真实的野菜用户（子账号），通过映射表按 `(合作方, external_user_id)` 唯一关联；各自独立钱包 |
| D3 | 开户时机 | **首次使用自动开户**（2026-10-28 确认“做法一”）：合作方不需要提前调用创建接口；写操作遇到未知 `external_user_id` 时自动开户；读操作不开户 |
| D4 | 子账号限制 | 随机用户名、无密码、无邮箱，不能通过任何方式登录网页；不发注册赠额、不参与邀请奖励和充值返现 |
| D5 | 认证 | 复用 `partner_oauth_clients`，新增服务端授权方式与专用 scope；支持新旧两把密钥并存轮换、出口 IP 白名单、限流、审计日志；写操作必须带 `Idempotency-Key` |
| D6 | 模型 Key | 额度不限，但花费受子账号钱包余额约束；长期有效，提供轮换；合作方被停用时其名下所有子账号的 Key 一并禁用 |
| D7 | 防滥用 | 每个合作方限制子账号总数与开户速率 |
| D8 | 付款位置 | 用户在合作方界面内完成付款 |

## Requirements

### R1 合作方服务端认证

- 合作方用 `client_id` 加服务端密钥换取短期访问令牌，令牌只能用于本任务新增的接口。
- 一个合作方最多同时有两把有效密钥：轮换时先发新密钥，合作方切换完成后再吊销旧的。密钥只展示一次，只存哈希。
- 可配置出口 IP 白名单；配置了白名单时，不在名单内的请求一律拒绝，包括换取令牌的请求。
- 按合作方限流，与现有 Partner OAuth 的按绑定限流互不影响。
- 合作方被停用或删除后，令牌立即失效。
- 只在主站 Host 提供；敏感响应 `no-store`；带 `X-Request-Id`。

### R2 子账号与自动开户

- 合作方以 `external_user_id`（长度与字符集有限制，具体见 Q7）标识自己的用户；同一合作方下唯一，不同合作方之间互不可见。
- **会开户的接口：** 领取或轮换 Key、充值或分配额度。遇到未知 `external_user_id` 时，在同一事务内开户并完成原操作。
- **不开户的接口：** 查询账号、余额、流水。遇到未知 `external_user_id` 返回 404，没有任何写入。
- 同一 `external_user_id` 并发首次请求时，只产生一个子账号，其余请求返回同一个账号。
- 达到子账号上限或开户速率上限时返回 429 或明确错误码，不建账号。

### R3 子账号属性

- 初始额度为 0；不发 `QuotaForNewUser`；没有邀请人，不给任何人发邀请奖励；所有订单或额度来源都不产生返现。
- 钱包账本完整：开户时写入不可退款的零额开户事件，与现有注册流程的钱包账本约定一致。之后每一笔入账都按返现契约写入 `WalletRefundCreditEvent`。
- 不能登录：密码登录、第三方 OAuth/OIDC 登录、Passkey、找回密码、“注册即登录”等全部路径都不能进入该账号，也不能为它创建个人访问令牌。
- 管理员能在后台识别出子账号及其所属合作方。
- 分组由合作方配置决定（Q3）。

### R4 模型 API Key

- 首次领取时发 Key；重复领取返回同一把 Key，不发第二把（Q5 若允许多把再调整）。
- 轮换：发一把新 Key，旧 Key 立即禁用（是否给宽限期在 design 阶段决定）。
- Key 长期有效、不设额度上限，但请求仍受子账号钱包余额约束，余额不足时模型接口照常拒绝。
- 子账号被停用或合作方被停用时，相关 Key 全部禁用，已禁用的 Key 不能通过再次领取绕过。

### R5 查询

- 账号：状态、钱包余额（内部额度和展示货币金额，口径同现有 `/api/integrations/v1/balance`）、累计消耗、创建时间。
- 流水：该子账号的入账记录（充值或分配）和消耗汇总，分页、有时间范围上限。具体字段在 design 阶段确定。

### R6 充值（取决于 Q1）

**若选 A（额度池）**
- 合作方有一个独立的预付额度池，管理员通过登记合作方付款为池子加额，并留审计记录。
- 分配接口必须带 `Idempotency-Key`。在同一事务内：池子扣减、子账号钱包增加、写分配记录和钱包入账事件。池子不足时整笔拒绝，不允许部分分配。
- 同一 Key 加相同请求体重放返回同一结果；相同 Key 但不同请求体返回 409。
- 钱包变更走现有额度防护（quota fence）和事务约定，不能绕过 Redis 缓存一致性。

**若选 B（Epay 订单）**
- 复用现有 Epay 下单、回调和入账逻辑，订单挂到子账号而不是 OAuth 绑定。金额、分组充值倍率、预设折扣、钱包容量与网页端一致。
- 幂等范围为“合作方 + Idempotency-Key”；限流按子账号和合作方两层。
- 订单返现上下文标记为不参与返现（不记录请求 IP/UA/设备）。
- 支付合规未确认时返回 503，与现有行为一致。

### R7 停用与管理

- 合作方可以停用单个子账号：Key 禁用，不能再充值或分配额度；余额保留。
- 管理员可以配置合作方的服务端模式：启用开关、IP 白名单、子账号上限、开户速率、分组，以及密钥的签发、轮换和吊销。敏感操作沿用现有的 `sensitive_write` 二次验证。
- 管理后台可以按合作方查看子账号列表。

### R8 审计

- 写入 `partner_oauth_authorization_logs`（或同表新增 action）：令牌签发失败、开户、Key 首次签发与轮换、充值或分配、停用、密钥轮换与吊销、IP 白名单拒绝。
- 不记录密钥、令牌、Key、`Idempotency-Key` 原文和请求体。

## Constraints

- **认证安全：** 按 AGENTS.md 6.2 对照 OWASP ASVS 5.0 及 OAuth 2.0、Authentication、Session Management、Secrets Management 等 Cheat Sheet。交付时列出引用的条目号、已验证项和未验证的缺口；存在缺口时不得声称合规。
- **计费与返现：** 遵守 `.agents/rules/billing.md` 的额度换算与安全不变量，以及 `.trellis/spec/backend/referral-recharge-cashback.md` 的事务、额度防护和钱包账本要求。若新增钱包入账来源（A 方案的池子分配），需同步更新返现契约。注意首充活动会把子账号的成功充值计为“已有充值”。
- **数据库验证：** 按用户要求只在一次性 Docker 容器中的 PostgreSQL 上验证（全新建表、从线上版本升级、重复迁移两次）。不跑 SQLite 和 MySQL，并在交付说明中如实写明，不声称三库兼容。
- **现有功能：** Partner OAuth 授权码流程、接口和数据行为保持不变；现有 `partner_oauth_payment_orders` 表的约束不修改。
- **文档：** 不在 `docs/` 新增文件，除非用户同意（Q11）。规则变化同步更新 `.trellis/spec/backend/partner-oauth.md` 或新契约文件。
- **Git：** 在 `feat/partner-accounts` 分支开发；只提交本任务文件、使用明确路径；不直接推送 `main`（合入即部署生产）。
- **代码改动：** 未经用户明确确认，不开始改代码；本 PRD 之后还需要 `design.md` 和 `implement.md` 并经用户审阅。

## Acceptance Criteria

- [ ] 用服务端密钥能换到访问令牌；密钥错误、被吊销、合作方停用、IP 不在白名单时分别被拒绝；两把密钥并存期间都可用，吊销旧密钥后旧密钥立即不可用。
- [ ] 对未知 `external_user_id` 首次领取 Key 时自动开户并返回 Key；重复和并发请求只产生一个子账号和一把 Key；查询未知 ID 返回 404，且没有写入。
- [ ] 子账号初始额度为 0，没有注册赠额、邀请奖励和返现，钱包开户事件存在；所有登录路径都无法进入子账号。
- [ ] Key 不设过期、不设上限；余额为 0 时模型请求被拒绝；轮换后旧 Key 失效；停用子账号或合作方后 Key 全部禁用，再次领取也拿不到可用的 Key。
- [ ] 达到子账号上限或开户速率上限时被拒绝，且不产生账号。
- [ ] 充值（按 Q1 选定的方案）：入账准确、幂等重放不重复入账、请求体不同返回 409、没有返现，额度防护和钱包事件完整。
- [ ] 审计日志覆盖 R8 列出的事件，且不含敏感值。
- [ ] 现有 Partner OAuth 的测试全部仍然通过。
- [ ] PostgreSQL（Docker）上全新建表、从线上版本升级、重复迁移两次均通过；交付说明写明只验证了 PostgreSQL。
- [ ] 后端测试、前端测试、类型检查和构建通过；OWASP 引用与缺口写入交付说明。

## Out of Scope

- 给合作方开 B2B 发票的自动化、自动结算或分成打款。
- Stripe、Creem、Waffo 等其他支付网关，订阅套餐购买。
- 支付平台退款或拒付的自动回调（沿用管理员登记）。
- 现有 Partner OAuth 的滑动续期（除非 Q12 决定要做，另开任务）。
- 子账号转为正常网页账号（Q9 决定后另开任务）。
