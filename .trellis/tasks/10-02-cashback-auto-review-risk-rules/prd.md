# 返现自动审核风险判断项可配置

## Goal

让 Root 自行选择哪些既有风险标记会拦下充值人返现的自动审核、转由管理员人工处理，同时不影响充值到账或绕过返现资金安全校验。

## Background / Confirmed Facts

- 用户截图显示“充值 IP 与账号首次记录 IP 不一致”“充值 IP 与近期登录不一致”“User-Agent 异常变化”。这些已是 `model/cashback_risk.go` 的风险标记；该文件另产生 19 种标记，`model/cashback_rewards.go` 还会在开放欠额时补充 `open_debt`，共 23 项。
- 当前正额充值人返现按免审总开关及低/中/高/严重四档“需人工审核”开关决定是否自动通过；邀请人始终人工审核。Root 设置在 Billing & Payment，管理员详情在 `/cashback` 审计展示风险证据。
- 配置通过版本锁原子保存于 Option；每笔返现保存当时配置/风险快照。既有规则规定缺失/非法设备线索不能阻断支付，单一 IP/设备关联不构成自动拒绝，零额/欠额等硬性资金阻断独立于审核策略。

## Requirements

1. Root 可逐项勾选**全部 23 项现有风险标记**作为正额充值人返现的转人工条件，而非仅截图三项；移除原四档人工审核设置及其新奖励决策作用。保留充值人免审总开关与“自动批准后立即发放”开关，邀请人仍始终人工审核。
2. 免审开启且逐项配置已显式保存时，任何被勾选的标记出现在新奖励风险快照中，该笔返现保持 `pending/frozen`，等待管理员人工审核；没有命中才可按现有安全规则自动批准/发放。只转人工，不自动拒绝、不拒绝正常充值到账。
3. 升级后新配置尚未显式保存时（即使旧的四档开关已设置、免审总开关开启），新奖励一律转人工，避免意外放款。其他配置的旧客户端或新客户端更新不得隐式启用逐项配置。Root 可明确保存**空选择**，该情形不因任何风险标记转人工；保存时必须清楚提示并确认该风险。
4. 已有开放欠额、零额取消、无资格、异常、额度 fence、对账、幂等、支付验签等硬性安全限制仍照常生效；`open_debt` 虽属于全部可见标记，但取消中的零额奖励不因勾选或取消勾选而转成可发放。配置变化不修改已有奖励的金额、状态、审核证据、风险/配置快照。
5. 管理端应能看出一笔新奖励因哪些勾选项转人工；风险证据只向有权限的管理员展示，不通过普通用户/公开接口暴露完整 IP、设备或审核策略。配置更新沿用 Root 权限与审计；界面文案支持七种语言。

## Acceptance Criteria

- [ ] Root 的表单展示全部 23 项风险标记且每项独立可选，保存/重新读取保持选择；原四档开关不再显示或影响新奖励审核，免审总开关与自动批准即时发放开关仍有效。
- [ ] 未配置、显式空列表、非空列表及免审总开关关闭四种状态的奖励结果明确：未配置/总开关关闭均待人工；空列表下正额合格奖励可自动通过；非空列表命中任一项则待人工并显示命中项，未命中则按现有自动批准路径。
- [ ] 首次保存空列表有明确的风险说明与确认；保存其他设置、旧客户端未带该字段、重复支付回调、错误或非法选项不会无意中启用配置、覆写已有列表、重复发放或绕过服务端校验。
- [ ] 待审奖励仍可按现有手审流程处理；邀请人、零额已取消、开放欠额及支付/结算硬阻断不变。已存在的奖励及历史快照不被重新分类或重算。
- [ ] Root 设置、Admin 详情、七语翻译、后台测试及相关真实 SQLite/MySQL/PostgreSQL Option/交易行为均得到验证；无法完成的验证须明确说明。

## Out of Scope

- 增加新的风险信号或风控评分算法、重新计算历史返现风险等级、按选项直接拒绝返现。
- 更改支付订单状态、付款渠道回调、邀请人返现审核及硬性债务/结算限制。
- 对旧 Option 行做破坏性迁移、回填历史审核来源或向普通用户展示管理员风险证据。
