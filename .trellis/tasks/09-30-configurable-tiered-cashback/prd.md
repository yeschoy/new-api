# 充值人及邀请人可配置阶梯返现

## Goal

运营分别配置充值人、邀请人的阶梯返现；每笔符合条件的充值按每个方向达到的最高档只发一次，不叠加档位，也不跨订单累计。访客在公开活动页能看到当前实际生效的规则。

## Background and decisions

- 现有返现按方向独立启用，策略为比例 `rate` 或每满 100 固定额 `per_hundred`；未选中的配置字段保留，以便切回。支付完成时保存配置快照，付款人的奖励需要活跃活动，邀请人的奖励不依赖活动。
- 两个方向各维护独立可编辑档位。门槛、奖励均以人民币元表示且允许精确到分；不可通过浮点金额决定支付奖励。用户给出的 100→5、200→15、500→40、1000→100 是示例，不得写成固定档位或强制默认。
- 每笔每方向选择门槛不高于该笔面额的最高一档。例如示例下充值 50 返 0、充值 200 返 15、充值超过 1000 仍返最高档 100；不叠加、不倍增、不跨订单累计。
- 当前 CNY 和 USD 面额按 1:1 处理；代币充值当前不用，Creem 不支持。新策略仅面向标准面额的在线充值，不改变现有策略对其他方式的行为，也不按支付折扣或事后汇率反推历史订单。
- 零奖励继续写库供按 ID 审计，但在返现审核列表、分页及对应计数中隐藏；现有风险、冻结、审核、发放、退款与欠款约束不放宽。
- 已上线 `/activity` 概述页。用户确认应向访客展示当前生效的具体规则及档位；现有 Root 专用 `/api/cashback/config` 不得直接公开。

## Requirements

1. Root 可为两个方向分别选择新增阶梯策略、增删编辑档位，并保存/读取精确到分的金额；可切回现有两策略，未选中的档位仍保留。旧客户端不传新字段时不得清空现有档位。
2. 服务器验证门槛与奖励为正数、最多两位小数，拒绝重复门槛、过量档位与溢出；启用阶梯策略必须配置至少一档。保留现有两方向合计返还不超过充值面额及单笔/24 小时额度限制；无效更新不得部分生效。
3. 在支付成功的交易中按订单面额快照选择最高档，以所选档固定返现金额计算钱包额度并应用既有限额。配置变更不追溯重算既有订单，结算重试不得重复发奖。
4. 付款人充值预估、订单列表与明细可区分阶梯、比例、每满 100 策略；预估不是支付/结算输入，实际规则仍以支付成功时配置为准。
5. `/activity` 通过只读公共接口展示当前生效的两个方向的实际策略与具体金额/档位，停用方向或无活跃付款人活动时不展示失效规则；不得泄露内部额度、审核政策、风控、用户及 Root 配置细节。接口失败时不应误称活动生效。展示金额明确标注人民币元。

## Acceptance criteria

- [ ] 独立设置两方向的 100.50→2.50 等档位可持久化、重新读取、切换策略后保留；重复门槛、三位小数、空启用档位、过大/溢出值和过度总返还均被服务端拒绝，原配置不变。
- [ ] 按同一笔订单验证门槛下方/恰好达档/两档之间/超过最高档（包括到分的边界），每方向只领取最高档的固定奖励，不跨订单累计；未达档的零额审计记录不进入审核列表或计数。
- [ ] 预估与实际按相同面额快照和所选档计奖，单笔和滚动 24 小时上限、活动次数、风险审核、冻结发放、退款与重复支付仍按既有规则执行；历史比例和每满 100 奖励不可被新配置重算。
- [ ] 匿名访客可看到当前生效的实际档位与其他现有策略规则，但看不到停用的付款人活动、停用方向或敏感管理配置；加载失败有明确降级状态。移动端、键盘操作和七种语言可用。
- [ ] 在任务专用 Docker 容器的真实 SQLite、MySQL、PostgreSQL 上验证配置保存/解析、奖励读写与计奖结果，并运行相关 Go/前端测试、typecheck、lint 和构建；缺少任一必需数据库验证须报告受阻而非声称完成。

## Out of scope

- 代币与 Creem 的阶梯返现计奖，以及现有两策略在这些支付方式上的修改。
- 追溯重算、补发或回填历史订单奖励；修改用户钱包额度单位或兑汇规则。
- 将用户给出的示例档位写死为默认规则。
