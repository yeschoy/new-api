# 技术设计：独立充值返现、分级审核和逐场活动

> 第一阶段门禁未通过，退款实施暂停：普通 API 预扣后退还与中途新充值/消费的反例，证明仅凭入账及最终余额不能保留历史归属；用户需决定是否允许仅对临时预扣净额重算。返现资格、活动与易支付 CNY 报价边界不变。此次不是并发压测问题，不能靠忽略并发消除。

## 1. 边界与既有合同

保留现有 `TopUp -> CashbackOrderContext -> CashbackReward -> cashback_settlement -> User.quota` 的主数据库事务链，仍只接已验签的在线支付成功路径。既有 `inviter` 与 `invitee` 枚举/API 值不改名：对外将后者展示为“充值人返现”，避免改写已存记录。邀请人方向的有效关系及人工审核保持；充值人方向不再依赖 `InviterId`。首次启用前订单不补发，已生成旧奖励可继续结算。

活动只约束充值人方向；`inviter_enabled` / `inviter_rate_bps` 仍是独立方向配置。`invitee_enabled` / `invitee_rate_bps` 仍为充值人方向总开关/比例，必须同时满足总开关与活动有效期才产生充值奖励。活动结束或次数用尽不抑制合格邀请人奖励。设置界面解释总开关与活动状态的区别，避免一个开关偷偷创建没有期限的活动。

## 2. 持久化与兼容

新增独立 `CashbackCampaign` 侧表（主库），保存 `id`、`start_at`、`end_at`、`stopped_at`、`max_rewards_per_user`、`created_by`、`stopped_by`、`created_at` 等审计字段。时间一律 Unix 秒，半开区间 `[start_at,end_at)`；提前结束后的有效上界为 `min(end_at,stopped_at)`。起止时间与上限在创建后不可改；无进行中/已安排活动的重叠区间。使用稳定的配置版本 Option 行串行化创建和提前结束操作，并在主库事务内检验重叠；校验当前/未来时间与正数上限，服务端自行判定状态（计划中、进行中、结束），不信任客户端时钟。

为 `CashbackOrderContext` 添加兼容旧行的 `campaign_id=0`：下单事务根据服务端当前时间/活动区间和总开关捕获活动归属，无活动即 0，不能在支付时补选新活动。`CashbackReward` 通过已有 `top_up_id` 关联订单上下文获取活动 ID，不重复添加活动列；仅新增可区分自动/管理员/历史审核来源的 `review_source`，活动筛选按上下文与奖励既有唯一 `top_up_id` 索引联查。旧订单/奖励保持无活动且可继续处置，不强制回填、删除或改写。旧审核来源为空时按已有 `reviewed_by` 推断展示而不回写历史。活动自身为历史证据，已生成奖励仍由既有配置/风险快照决定金额、审核与到期。MySQL 5.7.8、PostgreSQL 9.6、SQLite 不使用不兼容的部分索引、JSON 列或方言专用锁。

配置仍在 `cashback_setting.*` Option 命名空间增加仅充值方向的 `auto_review_enabled`、四档 `*_review_required` 及 `auto_review_immediate_issue`；主开关默认 false，低/中档默认为 false，高/严重档默认为 true，立即发放开关默认为 true（主开关关闭或对应风险档需人工时不生效）。配置 GET 返回实际值；旧客户端 PUT 缺少新字段时必须在同一锁定的更新事务内沿用当前值，不能把高/严重默认策略悄悄重置。既有字段仍按原完整替换校验，`first_enabled_at` 和版本继续由服务端管理；活动创建不把旧全局首次启用时间改写为每场时间。

## 3. 活动资格与计次

`InsertOnlineTopUp` 的同一事务写入活动 ID 和原有下单资格快照：只有下单时处于活动有效时间、充值总开关开启且已达到既有首次启用边界才绑定；同秒启用的顺序以已提交事务中活动的可见性/绑定结果为准。`CompleteTopUpCashbackTx` 在原支付事务内根据绑定活动 ID 读取/锁定活动，确认支付成功时间也在该活动有效区间、未提前结束且支付时充值总开关仍开启。付款后才创建的活动不能认领旧订单；活动结束后旧订单只完成普通充值，不生成充值方向奖励。邀请人方向按原首次启用、支付来源和关系规则独立判定。

先按方向筛选合格受益人，再沿现有 `lockCashbackUsersTx` 的升序用户锁，对每个受益人计算滚动 24 小时额度；充值方向同一用户锁内查询本活动中 `reward_quota>0` 的充值奖励数量，对照活动正数上限后才写奖励。零额保留为可解释的 `canceled` 记录、不消耗次数；次数已满则不创建新充值奖励，邀请人奖励可继续创建。已占次数的奖励即使后来被拒绝、取消、追回或退款，也以初次正额 `reward_quota` 持续计数。现有 `(top_up_id,direction)` 唯一索引及支付事务幂等保护重复回调；三方数据库下对并发订单测试锁序与封顶。

## 4. 风控与审核状态

`CashbackReward.validate` 按方向校验关系：邀请人奖励必须有有效、非自邀关系；充值人奖励允许 `inviter_id=0`，受益人必须是订单充值人，若有邀请人只作为可用风险证据。`cashbackHardBlockReasonTx` 对充值方向重查订单、充值人账号、完成来源、异常与欠额，但不因邀请人变化/失效阻断；邀请人方向保留完整原硬阻断。风险快照中邀请人聚集/关系年龄仅在有有效邀请人时计算，不将缺失邀请人误判为风险；IP/设备/支付/金额等信号仍覆盖充值方向。管理员列表、风险筛选和汇总持续展示高/严重风险（包括自动批准的记录）。

奖励创建时按支付时保存的配置和风险等级判定 `pending` 或 `approved`：仅充值方向且主开关开启、该等级无需人工审核时自动批准，写入 `review_source=automatic`、审核时间，保持 `reviewed_by=0`（与管理员 `review_source=manual`、`reviewed_by>0` 区分，不伪造管理员审计）。邀请人始终 `pending`。若自动批准且立即发放开关开启，单独将该奖励的 `available_at` 设为支付成功时间，并在同一经验证的支付成功事务中，在复核对账/硬阻断/额度、获得充值用户额度 fence 的前提下写主额度与唯一资金 mutation；T+N 不约束这一条奖励。开关关闭时虽自动批准但 `available_at` 仍为支付成功时间 + T+N；手工审核的两方向一律保留 T+N。后续配置变更或活动关闭不追溯改变已生成奖励状态和到期时间。

立即路径不可在支付事务内调用会开启另一事务的 `IssueCashbackReward` 或用未受 fence 保护的 DB/缓存调用；应将现有发行检查/额度 mutation 抽取为能在已有支付事务和已持有的付款人额度 fence 下复用的事务内逻辑，使用事务本身执行有界对账检查（避免对全局 `DB` 做嵌套查询导致 SQLite 单连接死锁）。五个支付渠道共同通过 `CompleteTopUpCashbackTx` 到达该逻辑，正常充值主额度及返现发放均应同提交/同回滚；若对账、Redis fence 或发放校验失败，则本次支付完成事务失败并交由已验证支付回调重试，不承诺绕过检查的即时入账。发放记录的尽力日志在提交后记录，不作为资金证据；主库唯一 mutation 和状态保证重复回调不会二次发放。

## 5. API / 管理端

Root 配置 GET/PUT 沿用原路由，新增审核策略与免审后立即发放字段，服务端校验并把变更字段纳入审计；易支付商户 CNY 收款确认作为独立的受审计 Root 配置，与当前商户身份/网关配置绑定，不能让旧确认跨商户复用；前端明确说明仅自动批准的充值奖励适用该开关，关闭开关仍有 T+N。活动采用 Root 权限的 `GET /api/cashback/campaigns`、`POST /api/cashback/campaigns`、`POST /api/cashback/campaigns/:id/stop`，创建/结束含稳定审计 action、权限与限流、时间与上限校验、并发创建防重叠；早停幂等，已结束活动不可重启或修改。活动列表可见开始/结束/早停时间、次数上限及创建人，返现详情可追溯关联的活动 ID；既有 Admin 奖励列表保持风险筛选，可按活动 ID 补充过滤。

复用现有 Root `CashbackSettingsForm` 与其 SettingsSwitch/Form 组合、已有输入与确认组件，在同一区域增加分级审核策略、易支付 CNY 收款确认和活动创建/列表/提前结束；复用 Admin `/cashback` 的现有风险过滤、表格与详情，调整方向文案、显示关联活动/自动审核来源。管理员退款区域显示仅易支付 CNY 的逐单现金报价、购买/赠送额度依据及不可自动报价的原因，确认前重新计算，其他渠道保持人工核对而不显示伪造的 CNY 总金额。i18n 用既有七个 locale 文件和项目翻译流程；不新增平行的第三方向或重复造表单/对话框。校验、完整配置替换及 API 类型在前后端同步。

## 6. 兼容、发布与回滚

新增侧表与尽量少的返现侧表列需纳入常规/快速 AutoMigrate，验证新库和最新发布版 `v1.0.0-rc.40` 的代表数据升级并重复迁移；若该发布版还没有返现侧表，也须测试当前分支旧返现数据的升级兼容。活动表只有新记录，旧 `campaign_id=0` 允许继续审核、到期结算与退款处置。新安装和升级均不自动造无限期活动；用户表示目前活动未开始，但线上现状尚未直接核实，发布前应检查实际开关与奖励数据。若发现实际正在进行的活动，需回到产品决策而非静默截断。

异常停用新计提：关闭充值总开关或提前结束当前活动；关闭只影响后续支付，已经生成的返现仍按快照处置。生产代码回滚前需评估已即时发放奖励：它们已混入可消费的主额度，不能靠回滚代码撤销；旧版不会识别活动上限，故应先停新订单计提。不得通过删除表或人工改余额回滚。

## 7. 退款时按需对账与手工给付

先挑战每次消费同步分配批次的必要性。在只有按时序可靠落库的入账与普通消费、没有来源指定的追回/退款时，各笔实际可用额度之和减去可信的当前 `User.quota`，可推得累计已消费额；退款时沿额度实际入账顺序模拟 FIFO，同笔购买与即时赠送为相邻段，例 A 总入账165、余额40，累计消费125，故可退35。日常 API 扣费和余额购买订阅不必因此逐笔写批次归属。单靠 `User` 的两个购买/赠送总数字段则不能保留旧批次赠送与新批次购买的先后关系。

最小持久化候选：主库侧表保存每个用户的启用边界/旧钱包余额（不可自动退款），以及带唯一业务键和有序 ID 的实际入账事件：已验签在线购买额、返现实际发放、注册/签到/兑换、管理员加额和邀请额度转入。支付成功事务与实际返现发行事务分别写入对应事件；迟发赠送在发行时新增段且保留原订单关联。低频非支付入账路径也要在同一资金事务中记证，不能用可关闭且尽力写入的 `LOG_DB`。账户的资金事件和钱包变更需按用户串行化，并在退款时核查证据完整；原 `User.quota` 仍是钱包总余额，不新增购买/赠送汇总列，不为普通 API 消费逐批次写扣减表。

阶段一只读核查已发现**确定性反例**（见 `research/current-state-and-constraints.md`）：旧购买100被预扣100，新购买50到账又消费40，旧预扣之后退还100，最终余额110；仅入账 `[100,50]` 与余额110 会推断旧购买剩60、新购买剩50，而按真实占用/退还顺序可能是旧购买恢复100、新购买剩10。预扣退还是否可视作撤销临时扣款并重算后续归属，待用户决定；未决定前不把简单公式作为准确现金报价的实现依据。

这一简化方案有前提，尚**不能**作为已验证设计：所有启用后的额度入账必须有可靠的来源、到账顺序与实际到账额，旧余额须有不可退款的起始边界；用户已确认迟发奖励仅在实际可用时进入顺序，不追溯改变此前消费归属：旧购买100→新购买50→消费105→旧单赠送10实际到账，剩余可退45购买，而不是50。退款、指定订单的返现追回/本金冲正、管理员更正、欠额、补偿与再次退款等不是普通消费，必须有足够的主库证据区分，不可把它们简单并入“累计消费”。现有消费日志可关闭、写入 `LOG_DB` 失败不阻断业务，且批量额度更新按用户聚合；不能拿它充当完整资金流水。`WalletFunding` 的预扣退款/结算也会用 `IncreaseUserQuota` 增额，这不是新增赠送或购买；预扣未结束时当前余额不代表最终消费，退款报价须等待可验证的结清状态或拒绝自动报价，不能把临时余额当准确结果。用户已确认无法可靠解释的管理员覆盖余额、欠额等异常账户显示“需人工核对”，不报自动可退金额；未结清的正常预扣则提示稍后重试，不能以故障值充当准确报价。现有额度 fence 和批量待刷新标记只能保证瞬时并发与已入队 delta，不证明此前预扣的 API 请求已经最终结算（`BillingSession.Refund` 还可能异步退还）。阶段一必须构造该反例验证；若成立，需在钱包预扣→结算/退还的**集中入口**加入最小的活动请求状态/失败待核对证据，跨实例且含无 Redis 模式，退款在无法证明确已结清时一律拒绝自动报价；这不是按批次分配消费。若要改动超出集中入口，停止并回到规划。需逐一验证现有各入账/特殊扣减路径（含签到、兑换、管理员 `add/subtract/override` 与邀请转入）是否已有可信证据，再决定最少补充哪些侧表或原有字段；优先新侧表，不在 `User` / `TopUp` 堆叠批次字段。

退款可退**额度**的 FIFO 计算与外部实际退还的**货币金额**是两个阶段。用户选择逐单按实付比例换算：每笔订单的现金可退金额以该单已核实的实付最小货币单位乘以该单未消费的购买额度，再除以原实际购买入账额度；赠送额度不参与分子/分母。统一在整数最小货币单位计算和向下取整，逐单累计给付不得超过已核实实付金额；同一订单多次退款要用累计目标差额而不是每次独立取整，避免反复舍入或重复给付。跨币种不能直接合计；用户确认**仅易支付且 CNY 实付可核实的订单有自动现金退款报价**，其他渠道仍参加返现活动、现金退款由管理员人工核对，不自动换汇。非易支付的到账额度仍需作为钱包 FIFO 消费来源，否则后续易支付订单的可退购买额度会算错；但其现金金额不纳入自动汇总。易支付验签数据有 `Money` 无币种字段，不能仅凭通道名断言商户实际以 CNY 收款。`TopUp.Money` 可受价格、分组倍率与折扣影响，不能把钱包额度直接标成元；它是下单金额，不能默认等同于网关实际扣款。Stripe Checkout 允许促销码，签名事件的 `amount_total` / `currency` 当前只在充值后写尽力日志，主库没有该实付证据。仅对易支付自动现金报价：须将验签 `Money` 解析为整数分，与订单应付金额及商户 CNY 收款配置/证据核对；金额异常不能给付充值额度/即时返现，也不能自动报价。通过检查后在支付完成事务内持久保存支付来源、金额与凭据（优先新侧表）；易支付协议本身无币种字段，Root 必须对当前商户/网关配置作可审计的 CNY 收款确认；支付网关地址或商户身份变更时旧确认失效，历史订单按创建/支付时绑定的确认与验签证据判断，不能借用新的确认。未确认时必须转人工。其他渠道无须为了现金报价改造五种回调的实付捕获，但其购买/赠送额度仍参与 FIFO；不能仅凭 `TopUp.Money` 对它们承诺 CNY 退款。

人工异常（管理员覆盖余额、来源不明、欠额、已有来源指定追回无法可靠重建、证据缺失）转人工核对；旧数据不可补造退款权利。常规消费将 `sum(有效入账及旧余额) - 已核对的钱包余额` 视为累计净消耗，按有序段 FIFO 算各单的未消费购买额度；每段实际发放的赠送额不可兑换。退款/奖励追回等来源指定扣减不得被误计为普通消费：有完整业务证据时作事件修正，不能证明时禁止自动报价。来自其他支付渠道的购买与赠送段仍在队列中，影响易支付段的剩余额度，但不自动报出其现金退款额。

退款显示只能是当前快照。确认退款时必须在钱包额度 fence / 未结清批量增量处理后，串行化读余额、重新计算并持久记录本次手工退款的金额、所涉订单、操作人和幂等键，同时处理相关赠送与钱包扣减；新侧表记录退款申请、逐订单扣回的剩余购买与已发赠送额度、对应 CNY 分、操作者、幂等键及待给付/已给付/失败需人工处置状态。先在 DB 事务内预留/扣除可退钱包额度并取消关联未发行赠送，再由管理员线下付款并记录完成；外部给付与数据库提交不可能天然原子化，付款失败只能经审计的人工补偿，不得无幂等重试扣款。既有 `HandleCashbackIncident` 按原单累计本金比例冲正，不能直接拿它执行跨订单未消费额度退款；如已有事件与本操作重叠，必须证明一致或转人工。若技术验证发现只记录入账和特殊变动不足以保证正常账户的精确结果，才讨论最小必要的扣费路径改造，不默认引入逐次消费分配表。无法解释的异常直接转人工，不能在前端显示猜测金额，也不能经自动确认流程执行退款。

活动仍需要独立 `CashbackCampaign` 持久化；只在已有 `CashbackOrderContext` 保存一处订单活动 ID，奖励通过订单联查，不改核心 `User` / `TopUp` / 消费日志表。若三数据库迁移审查表明增加返现侧表字段的风险更高，再评估独立关联侧表，不能以少列为由丢失下单时的活动快照。

## 8. 权衡与验证风险

- 选新增独立活动表 + 订单/奖励活动 ID，不复用不可重置的 `first_enabled_at`，以保证多场历史、同秒订单归属和计次可审计。
- 复用 `invitee` 枚举/配置 wire 字段而在 UI 改称“充值人”，减小旧数据库/API 升级爆炸半径；若日后重命名，另立兼容迁移。
- 只在创建时自动审核，后续不批量修改旧 `pending`，避免策略切换造成历史余额突然解冻。立即发放按单笔奖励的支付时快照决定，不追溯作用于旧 `approved/frozen`。已即时发放的奖励遇退款仍走原追回/欠额路径；到账后可立即消费使追回失败形成欠额，这是及时性相对于 T+N 的真实资金风险，需在产品审阅中明确。
- 数据库变更必须通过真实 SQLite/MySQL/PostgreSQL 矩阵、升级及重复启动。当前环境 Docker 守护进程未运行、`TEST_MYSQL_DSN` / `TEST_POSTGRES_DSN` 未配置，但本地 MySQL/PostgreSQL 二进制存在；实施阶段尝试隔离实例。无法跑齐矩阵时不得宣称 DB 兼容或任务完成。
