# 管理员 add 人民币面额留证：只读代码核查（2026-09-25）

## 已验证的现状

- `web/src/features/users/components/user-quota-dialog.tsx` 以当前展示币种输入金额，用 `parseQuotaFromDollars` 计算额度，POST `/api/user/manage` 只发 `{id,action:'add_quota',mode,value}`；`web/src/features/users/types.ts:ManageUserQuotaPayload` 和 `controller/user.go:ManageRequest` 均无原始金额/币种。`web/src/lib/format.ts:parseQuotaFromDollars` 对货币正数执行 `Math.round(amount / exchangeRate * quotaPerUnit)`，对 TOKENS 直接四舍五入；展示模式和汇率来自浏览器 `/api/status` 映射、持久化 store，可能滞后（`web/src/lib/status-query.ts`、`web/src/stores/system-config-store.ts`）。
- `web/src/lib/currency.ts` 的 CNY 展示汇率是 `usdExchangeRate`，表示 **1 USD 对多少 CNY**，不是支付实收价 `Price`；`QuotaPerUnit` 默认 500000。后端源码初始 `common.QuotaPerUnit=500000`（`common/constants.go`），`operation_setting.USDExchangeRate=7.3`（`setting/operation_setting/payment_setting_old.go`），`general_setting.QuotaDisplayType=USD`（`setting/operation_setting/general_setting.go`）。前端回退值却是 CNY/汇率 1（`web/src/stores/system-config-store.ts`）；这些默认值并不能证明当前生产商户的实际配置或“CNY/USD 永远 1:1”。`web/src/features/system-settings/general/pricing-section.tsx` 将币种、汇率作为单独 Option 请求保存；虽将额度单位输入框设为 disabled，通用 Option API 仍可更新 `QuotaPerUnit`。
- `controller/misc.go:GetStatus` 把当前进程的币种/汇率/额度单位分别返回。`model/option.go:UpdateOption` 先 `FirstOrCreate` + `Save`（均未检查 DB error），再更新本机 `OptionMap`/全局变量；`UpdateOptionsBulk` 虽一次提交多项，但提交后逐项更新内存。`model/option.go:updateOptionMap` 分开处理 `USDExchangeRate`、`QuotaPerUnit` 和 `general_setting.*`；旧 `DisplayInCurrencyEnabled` 还会**只修改运行时**展示模式（USD 或 TOKENS），不保证持久 `general_setting.quota_display_type` 与运行时相同。`SyncOptions` 定时从 DB 重载，跨实例可能暂时不一致。`setting/config/config.go` 的配置 getter 返回共享指针，当前没有可与 add 事务配对的不可变、版本化汇率快照。因此只读进程全局、浏览器 store 或当前 DB Option 值事后回算，均不能证明入账当时的 CNY 面额。
- `controller/user_quota.go` 调 `model.AdjustUserQuota`；它锁住目标用户、在主库事务内改 `User.quota`，`add` 同事务为 `AdminQuotaCreditEvidence` 写一条唯一 `event_key`、`credited_quota`、`credited_at`，但 `cny_cents` 目前保持 NULL（`model/user_quota_adjustment.go`、`model/admin_quota_credit_evidence.go`）。提交后的 Redis 增量、LOG_DB 审计不等同于金额来源；`subtract/override` 不写购买证据。现有表的 nullable `cny_cents` 足够表达新发生的管理员申报 CNY 面额，不需要加表、加列或每笔普通消费写入。

## 最小安全方案（**建议，未实施**）

1. 仅在管理员明确以 **CNY** 输入的新 `add` 上添加可选 `cny_cents` 请求字段（正整数分，由原始输入十进制解析，最多两位小数），保留已有 `value` 额度字段与现有换算语义；旧客户端缺字段继续入账，但证据中的 CNY 面额为 NULL。`USD/TOKENS/CUSTOM` 模式或币种不确定时，若没有另设明确 CNY 输入，**禁止**把它们的数值标成 CNY。受信任的不是前端所报金额，而是管理员作出的 CNY 业务面额声明经服务端验证与实际加额一致；它**不是收款凭据**。
2. 服务器在**同一个主库事务**内取得权威、稳定的转换条件和用户余额锁，对 `mode=add` 且提供 CNY 分的请求检查：有效 CNY 模式、有效正有限的 USD→CNY 汇率与额度单位；按整数分/精确十进制 `expectedQuota = roundHalfUp(cny_cents / 100 / usdToCnyRate * quotaPerUnit)`，要求 `expectedQuota == value > 0` 且落在钱包额度范围内（正数的 half-up 与当前前端 `Math.round` 对齐）。通过后余额变化和同一行证据原子提交。例：当前汇率确为 1 且单位为 500000 时，输入 ¥50.00 → `cny_cents=5000`，额度 25000000；若汇率是 7.3，仍应按入账时 7.3 换算额度，现金面额仍是管理员明确录入的 ¥50，不将内部额度误称人民币。不可从 `value / 当前 QuotaPerUnit * 当前汇率` 反推历史输入金额；不匹配要拒绝带面额请求，提示刷新/重试，而非写一个错误的非 NULL 面额。
3. **先补 Option 一致性门禁再开放非 NULL 写入。** 目前的 Option 保存机制不足以让“事务读取参数”成为当时有效参数：对相关设置 (`general_setting.quota_display_type`、`USDExchangeRate`、`QuotaPerUnit`，以及能覆盖展示模式的旧 `DisplayInCurrencyEnabled`) 建立共同的、预先存在的 Option 行串行化边界；add 与所有这些设置写入均在主库事务内以一致顺序锁定该行，读取同事务持久有效值，严格检查读写错误、缺失/非法/冲突配置；设置提交后再发布运行时缓存。SQLite 使用事务写串行化及冲突重试，MySQL/PostgreSQL 用行锁；不能仅锁读取侧或依赖不存在行上的 `FOR UPDATE`。避免旧设置 API 只更新内存但不更新 DB 的兼容覆盖；旧服务实例或绕开边界的写入混跑期间，关闭带 CNY 面额的 add/报价。这样不改变现有每笔加额的额度计算公式，只把**匹配性验证**和证据入库放进相同提交边界；浏览器缓存陈旧时拒绝，不悄悄变更入账额。
4. 若本轮不想改 Option 更新及多实例一致性边界，可采取更窄的有界模式：仅凭服务器明确固定、不可被旧接口更改的 `CNY` + `rate=1` + `QuotaPerUnit` 值计算并校验客户端 `value`，并在启动/请求时发现配置可变或来源不明即**拒绝带 `cny_cents` 的新请求**；旧 API 继续写 NULL、只能人工核价。现有代码尚无这个固定配置承诺，单靠用户口述“目前 1:1”、UI 默认汇率 1 或服务器当前内存值，不足以启用自动填面额。

**边界：** 即使上述门禁实现，一张 add 侧表只证明该次管理员业务面额与实加额度对应，不证明外部付款、其他渠道到账顺序、钱包最终已结清或所有历史批次；不能据此发布完整退款总额。需要聚焦检验汇率变更竞争、旧客户端 NULL、CNY 与 USD 模式区分、无效配置、四舍五入边界、事务回滚和三种数据库的新建/升级/重复迁移；本次仅源码只读核查，未运行集成测试，未核验生产 Option 值。
