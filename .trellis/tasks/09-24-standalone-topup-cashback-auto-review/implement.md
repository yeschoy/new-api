## 1. 退款按需计算方案先行验证（执行第一门禁，未完成前不写退款业务代码）

- [ ] 只读追踪所有钱包入账与特殊扣减（在线充值、实际返现发放、兑换、管理增减、邀请转入、退款/奖励追回/本金冲正、订阅/普通使用），分类哪些在主库有可靠来源、唯一事件和严格顺序；验证当前 `LOG_DB` 与批量计费不能作资金账本，核对易支付验签 `Money` 与实际 CNY 商户收款证据、订单金额及购买入账额度；其他渠道只需记录实际到账额度与时序以参与 FIFO，不为了现金报价扩展实付捕获。
- [ ] 用例 A/B 及迟发返现（先花新购买5再到账旧奖励10，可退45）、易支付 CNY 实付90/购买100/剩50兑付45及逐单累计取整、签名金额不匹配订单拒绝充值/返现、其他渠道参与 FIFO 但不自动给现金报价、退款后再充值、部分追回、欠额、管理员调整、同秒并发、Redis 批量未结清余额及 API 预扣未结算/退还验证“可靠入账与特殊变动 + 当前可信余额 → FIFO 可退额”是否充分；与现有按订单异常冲正的关系须明确。
- [ ] 若成立，补入账/特殊事件所需最少侧表和退款操作状态/幂等审计设计，尽量不改普通计费路径及原有表；管理员覆盖余额、欠额或来源不明等不能证明准确的账户转人工，不展示自动金额；未结清预扣只提示稍后重试。若正常账户仍存在反例，明确必要的最小改动并回到规划复核，不能返回貌似准确的金额。

## 3. 退款对账、确认与资金证据

- [ ] 在主库新增实际入账/旧余额边界与手工退款证据侧表；对支付成功、返现实际发行、注册/签到、兑换、管理员加额和邀请转入等低频入账记录唯一事件与到账顺序，保留非易支付的 FIFO 额度来源，不在 `User`/`TopUp` 增加购买/赠送分账列。各资金变更与证据同事务；缺证据、异常覆盖、欠额与旧余额不提供虚假自动现金金额。
- [ ] 易支付验签 `Money` 严格解析为整数分，与订单应付金额核对（不一致不得充值/即时返现），保存与支付订单同事务的金额凭据；Root 对商户 CNY 收款作审计确认并与商户配置绑定，更改网关/商户后确认失效。非易支付仍可计提返现，不自动报现金退款；同一钱包的非易支付入账参与 FIFO。
- [ ] 将预扣→结算/失败异步退还与退款报价并发写成可重现测试；若现有 fence/批量待刷新状态不能证明钱包已结清，只在集中钱包资金生命周期加最小状态证据，并在无 Redis、多实例/崩溃/失败路径同样拒绝不可信报价。不得默默把预扣当最终消费；超出集中入口的改造先回规划。
- [ ] 实现锁定钱包后的快照计算和确认时重算：按实际到账顺序还原各单未消费购买与关联赠送，CNY 分逐单累计比例换算及实付上限。退款预留/钱包扣减/取消未发赠送/幂等审计同主库事务，管理员线下给付后登记结果；失败人工补偿，不自动重复扣款。与旧 `HandleCashbackIncident` 有重叠而无法证明一致时转人工，绝不叠加执行冲正。
- [ ] 在现有模型/控制器适合的一个回归测试集覆盖 35/125/45、90→45、非易支付 FIFO、第二次报价、退款重试/并发、签到/兑换/调整、缺凭据、旧余额、欠额、预扣/批量不可信及赠送追回；必要时仅新增一个集中退款测试文件，避免跨层散落小测试。
