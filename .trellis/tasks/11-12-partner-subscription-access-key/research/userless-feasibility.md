# 不向 users 新增记录的可行性评估

## 1. 状态与结论

**后续决定：本期不采用此方案。** 用户获知改造范围后选择“修改比较大那就新增吧，但是得下单成功才新增users”。本记录仅保留无 users 可行性取证，不再注入实施上下文或执行相应零用户新增测试；精确开户时点在主 PRD 继续澄清。商户不传 external_user_id 保持确认。

最初询问为“可以做到不往users新增用户吗”，以下评估说明该未选方案的范围，不构成实施授权。

结论：**可以实现，但现有主链路不原生支持。必须以订阅为独立鉴权/计费主体，不是仅去掉 Create(User)。** 不创建或复用影子用户，不用 UserId=0/负数或全商户共享用户绕过授权。查询订阅 Key 和真实模型调用 API Key 仍为不同凭证。

本轮仅源码取证及方案讨论，没有业务代码、数据库、运行测试或生产操作。

## 2. 已验证的代码依赖

| 边界 | 当前证据 | 需要解决的问题 |
| --- | --- | --- |
| 模型凭证 | `model/token.go:14` 的 Token 带 UserId | 原有 Token 表/校验以用户为归属，不能仅插入无用户的普通 Token 并声称可用 |
| 订阅权益 | `model/subscription.go:265` 的 UserSubscription 带 UserId，按用户检索有效订阅 | 无用户订阅须直接定位自己的订阅实例/额度，不能归入一个共享用户 |
| 推理鉴权 | `middleware/auth.go:607` TokenAuth；`:686` 无条件 GetUserCache(token.UserId)，校验 User.Status/Group | 新调用凭证必须有明确、独立的 principal 分支，不伪造普通用户上下文 |
| 计费入口 | `service/billing_session.go:389` NewBillingSession 拒绝 UserId<=0，随后查询用户成员资格与钱包/订阅 | 需要订阅主体专用 funding/结算路径，不能只设置 UserId=0 继续普通链路 |
| 预扣/补扣/退款 | 同文件 BillingSession.Settle/Refund/Reserve 及 `service/quota.go:406` PreConsumeTokenQuota | 订阅主体自己的幂等预扣、实际结算与失败退款，不能错误增减旧 Token/用户额度 |
| 中转身份 | `relay/common/relay_info.go:86` 附近 RelayInfo 携带 UserId/TokenId/UserSetting，SubscriptionId 注释限定 user_subscriptions.id | 必须带主体类型与独立订阅/凭证 ID，不能让两个表的相同整数 ID 混用 |
| RPM | `middleware/model-rate-limit.go:37` 及 `:217` 以 userID/id 构造套餐和全局限流键 | 用类型分离的订阅主体限流键，不能所有无用户请求挤入 id=0 桶 |
| 日志/统计 | `service/quota.go:373` 更新用户使用统计、`:389` 记录以 UserId 归属的消耗日志 | 订阅/商户维度可追溯，不能写成用户 0 或污染普通注册用户统计 |

这些是源码证据，不表示所有协议/异步路径已经完成依赖穷举；最终设计需限定并检查实际 Coding 调用主链路，未知路径在安全适配前拒绝，不能悄悄回退普通用户权限。

## 3. 建议的无用户关系（待用户选择）

```text
商户 → 付费订单 → 可信支付/本地交付 → 独立商户订阅实例
                                       ├─ 查询订阅 Key
                                       ├─ 模型调用 API Key
                                       ├─ 套餐/分组/有效期/状态
                                       └─ 本周期总额/用量/预扣及结算记录
```

- 不需要 external_user_id，不写 users；内部也不创建“仅隐藏于列表”的实际用户。
- 新订阅实例归属 tenant_id + plan_id + 初始购买/订阅身份；模型调用 API Key 直接归属订阅，不再经 UserId 找它。
- 原 UserSubscription/Token 普通用户路径保持原契约。候选方案新增不依赖 UserId 的订阅实例和模型凭证存储；具体表名/可复用服务在正式设计中确定。
- 查询 sub_ 仍只能读对应订阅信息、当前额度及正常模型 API Key；不能用 sub_ 直接调用 Coding。调用 API Key 只能消耗绑定订阅，不能借同商户其他订阅或钱包兜底。
- 新主体类型由服务端根据已验证的模型凭证决定，不能由客户端指定 subject_type 或 subscription_id 改写。
- 新订阅到期或额度耗尽，订阅主体计费必须阻止调用；到期查询按已确认规则保留历史且不返回 api_key。重置 sub_ 不自动更换 Coding API Key。
- 同幂等购买/支付恢复只能创建一次订阅和凭证；显式续费目标的定位方案仍待收敛，已确认同一订阅续费沿用原 Key。

## 4. 改造范围与取舍

最小正确实现涉及：新无身份订单与交付关联、独立订阅/凭证持久化、模型鉴权 principal、分组/模型权限、订阅专用 funding 的预扣/结算/退款、RPM 主体、消耗日志归属，以及旧用户路径回归。

可复用：商户 pt_ 与专属套餐配置、价格/币种/支付验证、收银台、支付事实独立提交和恢复模式、模型上游适配器及套餐计价/周期计算基础。无需为此重写上游模型协议或新增买家登录系统。

不能保留此前“只改商户接口、不触及普通调用入口”的实施范围，也不能声称不需要用户就无需其他身份实体。这里以订阅实体取代用户承担调用与权益归属，复杂度高于自动创建内部用户，但边界更符合纯订阅凭证产品。

## 5. 必要验证与限制

沿用用户约束：仅本次必要定向测试，数据库只验证隔离 PostgreSQL（pq），Go runner/数据库用任务专属 Docker；不跑 SQLite/MySQL/无关全量测试。

如采用无用户方案，必要新增断言：

- 新购、交付、查询、模型调用及续费/重置前后 users 数量不增加，且不借用共享现有用户。
- 模型 API Key 确实执行请求并只预扣/结算其订阅；额度耗尽/到期拒绝，失败退款幂等，跨订阅/商户不能挪用。
- principal/限流/日志 ID 类型隔离，不以用户 0 聚合；新凭证无法获得普通用户/管理身份。
- 鉴权和统一计费确有触及时，做受影响普通用户路径的最小回归；这些是本次必要验证，不扩跑所有协议/前端。
- pq 增量/重复迁移和持久化不修改既有账户、订单或订阅；编译不冒充 runtime。

没有任何数据库测试或模型请求在本轮执行。采用该方向后需要重写 design.md / implement.md 并重新呈现最终摘要，获批后才可实施。
