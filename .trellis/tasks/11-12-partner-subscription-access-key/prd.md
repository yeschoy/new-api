# 商户开发者密钥下单与独立订阅 Key 查询

## 状态与原始需求

- 状态：planning；用户已选择 A：仅在支付渠道可信确认付款成功后新增内部 User，创建订单/返回付款 URL 不开户。商户不传 external_user_id 仍为硬约束；续费目标定位方式待确认。未批准实施，未运行 task.py start，未修改业务代码。
- 原始需求：“再新增一种对接方式，商户通过开发者秘钥鉴权来生成订阅订单接口”；用户进一步澄清付款后交付的是单独订阅 Key，另设接口通过此 Key 取得“订阅信息、剩余额度、apikey”，不是用它直接调用 Coding。
- 后续明确决定：商户后端领取并交付（A）；同一份订阅续费沿用原 Key（“要”）；到期可查历史但不返回 Coding API Key（“可以”）；本期增加商户端重置订阅 Key（“好”）。上述答复不等于最终技术方案已获实施批准。
- 用户新增约束：“记住写完之后只做有必要的测试，不需要做过多无关的测试”；进一步指定“不需要验证sqllite，只需要验证pq”。因此只做本功能必要的 PostgreSQL 验证，不运行 SQLite/MySQL 测试。
- 用户新增要求：“并且这里我需要为商户可以配置可订阅的套餐”，并选择 A：每商户可配置多份专属套餐，一份套餐只属于一个商户；另强调“订阅key是可以获取到信息的，是不需要再要商户秘钥来”。
- 最新纠正：“不是，商户下单时不会传external_user_id这个”。该要求优先于此前助手为复用旧流程添加的身份假设；旧 API 的必填字段不是新需求。
- 已评估无 users 方案，用户答复“修改比较大那就新增吧，但是得下单成功才新增users”，随后明确选择 A：付款成功后才新增用户。本期不实施无 users 独立主体，研究记录保留。

## 目标与用户价值

商户通过服务端开发者凭证创建付费订阅订单，买家付款后获得独立订阅凭证；买家无需持有商户秘密即可读取所购订阅权益及实际 Coding 调用凭证。既有商户 API 和可选托管 H5 保持可用，不要求调用方切换。

## 需求

| ID | 已确认要求 |
| --- | --- |
| R1 | 新增商户开发者密钥鉴权的无用户 ID 下单方式（见 R12），成功返回订单号和可打开付款的 checkout_url（平台收银台 URL），不预先交付订阅 Key 或 Coding API Key；复用支付基础设施，保留旧接入契约。 |
| R2 | 付款并交付完成后签发独立订阅 Key，与商户开发者密钥、Coding API Key 的秘密值和用途不同。 |
| R3 | 新增独立查询接口，**仅以订阅 Key 鉴权，不再要求商户开发者密钥、商户登录态或商户 ID**，返回该份订阅信息、实时剩余额度及实际 Coding API Key；终态限制见 R9。 |
| R4 | 订阅 Key 本身不能调用 Coding，也不能读取同账户其他订阅或其他用户的数据。 |
| R5 | 仅可信支付确认且本地交付完成才可领取；浏览器回跳、客户端已支付声明不能触发授权；重复通知和恢复不得重复签发或重复开通权益。 |
| R6 | 将订阅 Key 当作能读取 Coding API Key 的敏感凭证处理；不进入 URL、日志、公共缓存或无关响应。额度不允许因客户端数字精度丢失而失真。 |
| R7 | 采用商户交付：商户后端用开发者密钥领取其订单对应的订阅 Key，再根据自己保存的订单/购买意图交付。平台不要求商户提供买家 ID；公共收银台及 H5 不展示或返回订阅 Key。 |
| R8 | 同一份订阅续费保留原订阅 Key，查询展示更新后的有效期和当前额度。不同订阅及到期后新建的订阅不自动合并。 |
| R9 | 到期后原订阅 Key 仍可查看该订阅信息、已到期状态与历史额度统计，但不返回 Coding API Key；历史余额不表示可消费权益。 |
| R10 | 本期提供仅商户后端可调用的订阅 Key 重置能力；换发新 Key 并立即使旧订阅 Key 失效，不改 Coding API Key 或订阅权益。 |
| R11 | 采用 A（商户专属套餐）：平台管理员可为每商户配置多份套餐，一份套餐只归一个商户。复用现有套餐管理入口；商户仅能列出并新购自己名下已启用套餐，不能通过直接传未授权 plan_id 绕过，不新增多商户共享授权。 |
| R12 | 商户新接入下单不传 external_user_id 或其他终端用户身份；平台不能要求商户先开户、先登录或伪造用户 ID。订单幂等表示购买意图，不充当用户身份；内部关联由平台维护，续费显式定位方式待收敛。 |
| R13 | 采用 A：仅在支付渠道可信确认付款成功后，首次新购才自动新增真实 users 记录及关联凭证/订阅。创建订单、返回付款 URL、未付/支付失败/未付超时均不开户；若之后收到可信迟付，仍按已付交付。同订单通知/交付重试不重复新增，续费复用原用户。交付失败不留下部分用户/凭证/权益，已确认支付事实保留以便恢复。 |

## 范围边界

- 本期包含商户可订阅套餐配置、服务端凭证签发、商户领取、专用查询、商户重置、迁移、必要测试、接入文档与安全规范；优先复用已有后台入口，不新增面向买家的平台页面或商户 webhook。
- 不按商户 external_user_id 识别或复用新方式买家；首次新购仅在可信付款成功后的原子交付内建立内部用户及订阅/Token 关联，不把所有新购挂到商户共享用户。未支付订单不产生 User。
- 不实施无 users 独立主体，不使用用户 0/负数或共享用户替代真实关联；沿用原用户鉴权、订阅计费、RPM 与日志基础设施，保留旧接入数据和契约。
- 不更改套餐价格、额度单位、支付渠道或普通用户计费算法；同一购买的重试和恢复不重复开户，续费沿用已有关系的具体定位仍待确认。
- 不自动给历史已交付订单补签 Key，不改变历史订单及账户。新发生的真实付费续期可首次为其关联订阅建立凭证，不靠 GET 开户、授予或补发。
- 重置只阻止旧订阅 Key 的后续使用，不能撤回此前已经取走的 Coding API Key 或已经发送的查询响应；不增加 Coding API Key 自动轮换、根秘密轮换/KMS、独立撤销开关或自动退款。
- 不包含生产访问、上线、真实付款、未跟踪私钥读取、已有测试数据删除或未经用户同意的临时资源清理。
