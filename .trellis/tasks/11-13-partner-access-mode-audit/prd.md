# 商户接入方式互斥与订阅 Key 授权审计

## Goal

管理员创建商户时仅启用一种购买接入方式，默认免用户 ID「订阅 Key API」，可明确改选「平台托管 H5」；后端执行隔离，后台可以安全追溯订阅凭证签发、访问和拒绝结果。

## Background and evidence

- `controller/partner_tenant_subscription_key.go:114`：新购只解析 plan_id/payment_method，X-Subscription-Key 选择续费，不需要买家 ID。
- `model/partner_tenant.go:35`：商户已有专属分组，但没有商户级接入方式字段。
- `.trellis/spec/backend/partner-subscription-key.md`：现状为新旧入口并存，内部真实用户保持专属分组、订阅专用计费和 paid-only provisioning。
- `model/partner_oauth_authorization_log.go:18`：现有授权日志覆盖 OAuth/旧 server/account，缺少 tenant/order/subscription 关联及新模式事件。
- `web/src/features/partner-oauth-clients/authorization-logs.tsx`：已有独立后台授权日志查询页，可扩展而无需重复页面。
- 用户说明“现在没有商户，全部默认是订阅key”；这是产品/部署背景说明，并非生产数据库核验或删除数据授权。详细源码边界见 `research/current-boundaries.md`。

## Confirmed requirements

| ID | Requirement |
| --- | --- |
| R1 | 创建商户只能选择一种接入方式，由后端限制实际入口，不能只是界面标记。 |
| R2 | 只有订阅 Key API / 托管 H5 两种选项。H5 保留现有 external_user_id 要求；旧 external API 不再作为独立购买方式提供。H5 所需查单、账户 Key 和额度等辅助接口不等于允许绕过 H5 直接下单。 |
| R3 | 完整记录凭证签发、订阅 Key 领取/重置、鉴权失败及方式不匹配拒绝；每次成功的独立订阅查询也记录，包括到期/取消等不返回 Coding Key 的正常查询。后台可按商户、事件、结果和时间查看/筛选，接受成功查询产生的额外日志量。 |
| R4 | 订阅 Key API 新购不传用户 ID，可信付款成功后才原子创建内部用户及凭证；续费复用原关系。专属分组、商户套餐归属、订阅专用计费和精确额度协议保持。 |
| R5 | 日志仅安全元数据，不保存 pt_/sub_/sk_ 明文、原始鉴权头、请求/响应体、派生材料或能力 URL；未知凭证不伪造商户/用户归属，不伪装成 OAuth 用户同意。 |
| R6 | 默认订阅 Key：创建表单、创建请求省略模式、数据库增量字段的默认/空历史值回填均使用 subscription_key；未知值、显式空值/null 不按默认放行。不建立历史兼容模式、不依订单猜测分类、不删除或改绑账户/订单。 |
| R7 | 接入方式创建后固定；本期不提供模式切换 UI/API，密钥轮换和状态操作也不能顺带修改模式。 |

## Acceptance criteria

| ID | Requirements | Observable result |
| --- | --- | --- |
| AC1 | R1/R2/R6 | 默认创建为 subscription_key；只有明确选择 hosted_h5 才启用 H5；非法/空/null/旧兼容值不能创建。两模式的禁止购买入口直接 HTTP 调用也无订单/会话/开户/网关准备副作用。 |
| AC2 | R3 | 每次成功独立查询及批准的签发/领取/重置/拒绝有安全事件；后台按真实商户 ID、事件、结果、时间查询；未知凭证事件不虚构商户或 OAuth client_id。正常日志库可用时实际写入并可读；日志库故障的保证边界见设计风险。 |
| AC3 | R4 | 无买家 ID 新购、原 sub_ 同订阅续费、paid-only 原子交付及专属分组不回归；只读查单不开户/准备支付，额度保持十进制字符串精度。H5 原有身份、会话期限和一次购买/恢复协议保持。 |
| AC4 | R5 | 凭证可在允许的响应中交付，但不进入日志库、后台 DTO、筛选、错误输出或请求转储；只有授权管理者能读取日志。 |
| AC5 | R4/R6 | fresh/upgrade/repeat 增量迁移保留原账户/订单/支付事实及已明确设置的 H5；无历史兼容模式。收银台、可信回调和已接受订单恢复不被入口限制错误拦截。 |
| AC6 | R7 | 管理列表准确展示模式；无切换控件/接口；尝试通过状态更新、轮换或附加字段改模式不能成功或被静默当作已修改。 |

## Out of scope

- 普通 OAuth 同意、pst_ 钱包接入、普通计费/模型请求日志、支付对账体系重写。
- 免用户 ID 的 H5、模式切换、跨套餐升级、Coding Key 轮换、webhook、历史凭证补签/改绑。
- 生产访问/部署、真实付款、破坏性 DDL/清理、用户既有私钥及临时产物处理。
- 不因“目前无商户”删除共享支付能力、旧内部身份数据或现有 OAuth/server 日志。

## Risks and verification boundaries

- 所有成功查询会增加日志量；本期不采样或新增日志清理策略。
- 沿用既有独立 LOG_DB 最佳努力写入：故障输出脱敏服务告警，不回滚已支付事实/凭证操作，不承诺日志库宕机或进程崩溃时零丢失；不新增 outbox/跨库事务。该技术保证在最终摘要明确披露。
- PostgreSQL 为受影响迁移/持久化的必要运行验收目标，Go 测试仅在任务专属 Docker 中执行；其他引擎保留代码支持但不以它们替代 pq。ClickHouse 升级必须有明确增量 DDL 和相应检查；未实跑项单列，不能称全引擎验收。
- 实施检查点已有前端/静态与独立源码审阅证据；Go 编译/测试、数据库及真实支付验证尚未执行，详见 verification.md。中间非业务产物已登记，需用户同意才清理；Trellis 记录保留，npm/pnpm 缓存和诊断文件保持忽略。
