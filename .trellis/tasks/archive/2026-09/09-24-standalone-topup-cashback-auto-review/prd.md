# 独立充值返现、分级免审与逐场活动

## Goal

让合格在线充值用户无论是否有邀请人，都可在充值返现活动中获得返现；邀请人返现独立运行。管理员可按风险等级配置充值返现审核策略，并选择免审后是否立即发放（默认立即发放）。每场活动有明确期限和单用户次数上限。退款只提供管理员只读的已记录区间消费、逐笔购买额度剩余和参考金额，不由系统执行退款。

> **范围边界**：退款功能仅为只读参考报表；管理员负责实际给付及后续额度、返现处置。本次仅增加一张低频、有序的真实入账证据侧表，不建退款确认/钱包生命周期表、不在每次消费时新增写入。管理员查询前负责停止新使用并确认相关业务已结算；报表**按钱包余额已最终落库、没有在途预扣/异步退款**这一业务假设计算参考值，不为此增加持久的请求生命周期证明。既有消费日志不是可靠资金流水，区间消费只能称为「已记录消费」；退款总额仍须从完整有序入账与可解释的最终钱包余额独立推算，其他证据不全时提示人工核对。

## Background / Confirmed Facts

- 用户确认只有两类奖励：充值用户返现和邀请人返现，没有第三类“被邀请人返现”。用户说明目前活动均未开始；该业务现状未通过生产库验证。
- 现有 `CashbackDirectionInvitee` 对应充值用户奖励，但 `model/cashback_rewards.go` 先要求有效邀请关系才创建任何奖励。`model/cashback.go`、`model/cashback_state.go`、`model/cashback_risk.go` 的校验、硬阻断和风控也依赖邀请人。
- 现有配置以 `invitee_enabled` / `invitee_rate_bps` 表示充值用户方向，`model/cashback_config.go` 的 `first_enabled_at` 仅记录全局首次启用时间；尚无逐场活动、结束时间、次数上限或分级免审配置。奖励创建为 `pending/frozen`，结算仅处理 `approved/frozen`。
- 旧合同 `.trellis/spec/backend/referral-recharge-cashback.md` 与归档任务 `09-15-referral-recharge-cashback/prd.md` 明定“无邀请关系”为硬阻断且全部人工审核；这些规则须按本次新需求有界更新。现有合格来源只包括已验签的在线充值，非线上补单等路径仍排除。
- `User.quota` 只有混合余额，消费时不记录“先花购买额度再花赠送额度”的来源归属。`model/cashback_state.go:HandleCashbackIncident` 仅对指定订单先追回已发奖励、再按累计比例冲正该订单实际入账额，余额不足记录欠额；无支付渠道原路退款操作。相关既有回归测试 `TestCashbackIncidentIsMonotonicIdempotentAndCreatesDebt` 已运行通过，但未覆盖用户的跨订单例子。
- 用户澄清退款由管理员手工给付，想在申请时对账可退款额，不要求支付渠道自动退款。消费顺序是**按充值批次从旧到新**，先花某次充值的购买额度，再花该次的赠送额度，才进入下一次充值；未使用的赠送额度不可退款。我之前将其误解成“全局所有购买额度优先”，这一诊断已被用户纠正。
- 以下额度与现金示例假设实付/购买额度为 1:1。示例 A：day1 购买100+赠10，消费105 后，day1 购买耗尽、赠余5；day2 购买50+赠5，之后消费20时先花旧赠5、再花 day2 购买15，故 day2 购买余35、赠余5，可手工退款35。示例 B：day1 购买100+赠10，消费25 后购买余75、赠余10；day2 购买50+赠5，尚未再消费，购买余额共125、赠送共15，可手工退款125。
- 用户确认旧系统上线前已有的混合钱包余额无法可靠重建购买/赠送归属：这部分保持管理员人工核对；仅对新对账规则启用后形成且证据完整的批次自动计算可退金额，不把存量余额自动算成可退。
- 原先仅已验签在线支付订单可作为可退购买批次；用户现补充：**管理员正向加额（入账）也作为普通充值额度批次，按到账时间参加 FIFO**，而不是缺席导致误算消费。`subtract/override` 不属于充值，仍须特殊核对。用户进一步确认管理员正向入账剩余额度也按 **1:1 CNY** 给出手工退款参考金额（这是业务折算约定，不等于支付凭据）。按本次只考虑 CNY 的范围，管理员加额**输入的人民币金额是多少，就按多少元留证**；不为留证改动原表单已有的额度换算或实际加额额度。用户所说的 1:1 是这笔管理员声明的现金面额本身，不是要把钱包内部额度强制改按另一个汇率计算。仅当表单明确以 CNY 输入时，同事务存输入的人民币分和原逻辑产生的实际额度；其它展示币种或 token 输入不能冒充 CNY 面额，仍可加额但面额未知。旧记录不能倒推当时输入。管理员前端目前会按展示币种/汇率把输入金额换算成 `quota`，接口只提交额度和操作方式，没有持久保存原始输入币种/金额/汇率；缺少当时 CNY 面额的旧入账由管理员人工核对，不按当前汇率倒推。新增持久字段/表前仍须提供完整结构并获明确确认。用户最终纠正：**额度兑换码（`plan_id=0`）成功兑换会增加钱包额度，按实际到账时间作为不可退款批次参与 FIFO，但其剩余额度绝不可折算现金退款**；此前误写为可退购买批次的规划已撤销。订阅套餐兑换码（`plan_id>0`）只创建独立套餐权益、不增加 `User.quota`，套餐用量不算钱包消费；用钱包余额购买套餐则是钱包扣款。邀请额度转入等其他入账同样按到账时间排队但不可退款。余额购买订阅也会从 `User.quota` 扣款（`model/subscription.go`），当前与 API 消费一样未标注来源。用户希望在退款时按批次计算，尽量不改日常计费；可靠入账与余额的精确性仍须验证。
- 用户确认延迟审核/结算的赠送额度只从**实际入账时**进入消费顺序，不追溯重算之前的消费。例如 day1 充值100、赠10待审核，day2 充值50后先消费105，此时旧购买100与新购买5被消费；其后赠10到账，day2 尚余购买45，可退45（赠10不可退）。同一 API 请求的临时预扣与后续退还则按**最终净消费**抵消，允许在退款对账时重算它们造成的暂时性批次占用；此规则不把迟发的真实赠送提前。
- 用户确认手工给付的实际货币金额须按每笔已验签订单的**实付金额比例**换算该订单尚未消费的购买额度，而不是按额度面值给付；赠送额度不可兑付。现有 `TopUp.Money` 可能因价格、分组倍率、折扣与购买入账额度不同。用户将系统自动退款报价限定为**易支付且可确认 CNY 实付**的订单；其他渠道仍参与充值返现，但退款由管理员人工核对，不自动换汇。易支付验签结果包含签名金额但不包含币种，因此只有商户实际 CNY 收款已获管理员确认时，才能自动报出人民币金额。
- 用户此前说明手工给付按当时未消费的购买额度全额计算，不自行填入较小额度：原购 50、已消费 15 时参考 35（1:1），购买额度 100、实付 90、余额 50 时参考 45。但系统不登记或确认给付，不能据此保证同一订单不会在外部重复退款，管理员必须人工核对已退款历史。
- 用户最终将退款功能收敛为**只读金额与区间明细报告**，实际退款、钱包调整及两类返现的取消/追回均由管理员手工完成；此前拟议的系统确认/追回已撤出本次范围。两次充值之间的消费总额用于 FIFO 推算；赠送额度可被消费但**不可退款**。

## Requirements

1. **两类奖励独立**：充值方向开启且存在有效活动时，符合条件的充值用户无论是否有邀请人都至多生成一条充值奖励；邀请人方向只在有效邀请关系且其开关开启时至多生成一条邀请人奖励。充值用户活动结束、次数用尽或尚未创建活动，不阻止单独计提邀请人奖励。
2. **充值方向分级审核**：仅充值返现有审核策略开关，默认关闭；关闭时所有充值奖励人工审核。开启时按 `low`、`medium`、`high`、`severe` 四档分别设置是否人工审核；默认低/中自动批准，高/严重人工审核，各档可独立调整。邀请人奖励始终人工审核；高/严重风险订单仍须在后台可见。
3. **免审后发放时机**：另设仅作用于自动批准的充值奖励的“免审后立即发放”开关，默认开启。开启时，在支付验签成功且满足资金检查后跳过 T+N 立即发放；关闭时虽然自动批准，仍等 T+N 到期。需人工审核的充值奖励与邀请人奖励保持原 T+N。支付验证、合规、次数/额度上限、退款/欠额硬阻断、对账与防重复发放在任何模式下均不能绕过。
4. **逐场活动**：管理员显式创建并启用充值返现活动，每场持久记录开始、结束时间和每个充值用户的正整数返现次数上限（创建表单默认 1 次）。活动互不重叠；开始后起止时间不可修改，允许提前结束。下一场独立计数。只有同一活动有效期内下单且支付成功的订单有资格；提前结束后尚未付款的订单不再生成该场充值奖励，已生成的奖励按快照处理。
5. **计次与幂等**：仅生成正额充值奖励时占用本场一次；零额不占；此后即使奖励被驳回、取消或订单退款，也不返还次数。并发充值、重复支付回调与任务重试不能超过用户次数上限或重复发放。邀请人返现不消耗此次数，也不受活动时间约束。
6. **配置与兼容**：管理端配置、列表、详情及文案明确区分充值人和邀请人返现，不新增第三种奖励；保留现有 `invitee_*` 配置/API 值与已生成奖励的兼容性。调整配置不追溯重算奖励。上线不自动生成历史活动；管理员创建首场活动前不新增充值用户返现，但旧奖励继续结算，邀请人返现继续独立运行。
7. **只读退款参考报表**：管理员按用户查询每次充值到账前、两次充值之间和最后一次充值后的**已记录消费**汇总，而非逐次消费明细；区间汇总允许不完整，不能冒充真实消费总量。逐笔剩余与总参考金额须独立依据完整有序的真实入账（包括管理员正向加额购买批次、额度兑换码等不可退款批次及已实际发放赠送）及可信已结清钱包余额，按 FIFO 推算累计净消费，不依赖区间日志的完整性。每笔先花购买再花当时可用的该笔赠送，之后再花新批次；迟发赠送仅在实际入账时加入，普通预扣/退还只按完成后的最终净消费核算。赠送额度绝不计入退款。按每笔未消费购买额度占原购买额度的比例换算实付现金，易支付订单须由管理员在查询时明确确认商户实际收款为 CNY，方按验签实付金额给出人工退款参考额；该确认不是支付协议签名的币种证明，不称系统已核实 CNY，不跨币种合计；管理员正向入账按已记录的原输入 CNY 面额折算未消费额度；额度兑换码虽影响后续 FIFO 消费顺序，但自身不可退款、不得列入现金报价。其他渠道的额度参与 FIFO、现金金额由管理员核对。旧混合余额及已经手工退款的订单不能通过现有数据自动认定可退，须人工核对。

   报表从已有数据只读查询，不登记退款、不扣钱包、不自动取消/追回返现、不在日常消费时增写记录。区间消费日志可能关闭或写入失败，且订阅余额购买等扣款未必在同一消费日志；即使钱包余额与所有入账可以核对，仍不能证明**每个区间**日志完整，但这不妨碍在完整有序入账、所有其他变动可解释且余额可信的普通 FIFO 情况下独立计算最终批次剩余。本轮按管理员保证已结算、批量余额已落库的前提读取钱包余额，不主动证明中间态；若此假设不成立，参考值可能变化。缺失真实入账/特殊扣款来源、管理员覆盖、债务或支付币种/实付不确定时不显示貌似准确的现金总额，提示人工核对。若仅能得到日志区间合计，须明确标为「已记录消费（参考）」而非实际消费总额；不得把区间汇总当成计算总可退额的权威输入。
8. **运维范围**：保留现有首次启用边界、风控展示与审计。管理员手工补单、订阅、兑换码、注册赠送等仍不计提返现。本次不接自动退款回调或现金提现。

## Acceptance Criteria

- [ ] 无邀请关系：活动有效且充值方向开启时，一笔已验签的在线充值只生成一条充值用户奖励；没有邀请人奖励。有有效关系时，按各自开关最多生成充值与邀请人各一条，绝无第三方向。
- [ ] 无活动、活动未开始/结束、订单在活动外下单或支付、充值人的本场正额奖励次数用尽时，不新增充值奖励；独立启用的邀请人奖励仍按有效邀请关系生成。
- [ ] 两场活动记录有不同 ID、起止时间与逐场次数上限，互不重叠；已开始的起止时间不可修改，提前结束只阻止新计提而不改写已有奖励。
- [ ] 正额充值奖励只占本场一次；零额不占，驳回/取消/退款不退次数；并发成功订单也不超限，重复回调与重复结算至多计提/发放一次。
- [ ] 审核策略开关关闭时两类奖励均需人工审核；开启时充值方向按四档策略自动批准或进入待审核，默认低/中自动、高/严重人工；邀请人始终人工。
- [ ] “免审后立即发放”默认开启：自动批准的正额充值奖励在支付成功且通过资金校验后及时发放，T+N 不再阻止它；关闭后自动批准但仍冻结至 T+N。待人工审核的两类奖励继续受 T+N 限制。资金校验失败不得发放，无论重试多少次都不能重复发放。
- [ ] 自动批准的高/严重风险充值奖励仍在管理员风险筛选、摘要和详情中清楚显示；配置变化、审核来源及活动启停可审计。
- [ ] 旧配置缺少新字段时有安全默认值，旧 API 字段及旧奖励保留；不回溯补发、手工补单不计提。只读报表对旧混合余额、欠额、旧退款及无法解释的资金变动提示人工核对；普通 FIFO 的最终购买额度剩余可由完整有序入账与可信余额计算，日志不完整只降低区间明细的精度，不能把余额对齐冒充逐区间准确性。
- [ ] 证据完整的示例 A：旧购买100+赠10，消费105；新购买50+赠5，再消费20，旧赠送余5先用，新购买余35、赠送余5，参考购买额度35。示例 B：旧批次消费25 后旧购买余75，新购买50，全体赠送15 不可退，参考购买额度125。迟发赠送：旧购买100、新购买50、消费105、旧单赠10后发放，参考新购买剩45。预扣100→新充值50→消费40→预扣退还100，在可确认结清后按净消费40重算，旧购买余60、新购买余50。购买100、实付90、购买余50的易支付 CNY 订单参考现金45；赠送不参与换算。所有数额只在依据足够时显示为参考，不等于已经给付。
- [ ] 退款界面展示每个充值区间的**已记录消费**汇总与每笔购买/赠送剩余的独立 FIFO 推算依据，不显示逐次消费明细；**仅日志缺失**不应抹去资金证据完整时能由余额算出的最终剩余，但区间必须标为参考。非易支付/未证实 CNY、旧余额或来源不明时无已核实现金总额，转人工核对；系统不自动核验是否仍有在途资金，报表注明已结算假设。刷新只读不改变钱包、奖励或退款状态；相同余额但不同区间消费分布的测试应保留相同最终 FIFO 剩余，同时不误判区间已核实。管理端设置/活动操作和审核展示支持七种语言、服务端和前端校验一致；聚焦测试覆盖资格、四档策略、立即发放开/关及资金失败重试、活动边界/并发计次、T+N、幂等和旧数据兼容，并实际验证 SQLite、MySQL、PostgreSQL 的新建与升级迁移及重复启动。

## Implementation Boundary

- 用户已批准 `design.md` §7 的单张管理员正向入账证据侧表，同时明确普通每次消费**不增加写入**。每次 `add` 的额度证据与钱包同事务写入；CNY 展示下管理员输入的正金额若能精确表述为整数分，则在同一行留证，旧客户端/其他币种/不可精确到分的原有输入继续加额但面额 NULL。`subtract/override` 仍非充值，完整退款总额的证据缺口不因这一张表自动消失。
- 用户随后明确批准一张**统一有序入账证据侧表**：只在实际钱包入账或已知异常余额变动时，与原余额变更同一主库事务写入；记录非可退的旧余额开口，跨在线购买、实际返现发放、额度码、注册/签到、邀请额度转入、管理员 add 等来源排序；管理员 subtract/override 和来源指定冲正写异常标记，相关用户不自动报价。不改 `User`/`TopUp` 列，不回填历史可退批次、不新增普通消费写入。易支付币种由管理员在报表查询时确认后才按已验签金额显示**人工参考额**，不是系统验签币种，也不新增商户确认表/绑定列。旧账户若缺开口、新旧服务混跑或有未知入账/异常，标人工核对；管理员负责确认查询时已结算。新侧表的实际字段、索引、迁移和回滚在 `design.md` §7 限定。
- 用户最终明确：**尽量不影响既有代码和操作；管理员调整的金额是多少，就记录多少金额**。本次不新增另一种充值模式，也不变更原加额计算/入账额度。原表单在明确 CNY 展示时，把管理员输入的 CNY 金额作为业务声明面额，以整数分和原额度在同一事务留证；旧客户端、USD/token/其它币种输入仍按原逻辑加额，但 `cny_cents=NULL`，由管理员人工核价。服务端校验正整数分/范围、只限 add，不把金额称作验签实付；不从额度或今日汇率反推。此前未提交的强制 1:1 额度换算与替换表单默认输入，必须撤回；普通消费、全站配置及 Option 写路径均不改。

## Out of Scope

- 第三种“被邀请人返现”、多级分销、活动日期重叠或修改已开始活动的起止时间。
- 给首次启用前、活动期外或历史订单补发；把手工补单、订阅、兑换、注册赠送纳入**返现计提活动**；额度兑换码仅作为不可退款钱包批次参与 FIFO，不因此自动获取充值返现。
- 绕过支付验签、次数/额度、欠额/退款、对账、防重复发放，或新增自动退款/拒付回调和现金提现。
- 系统退款确认/防重复给付、钱包扣减、两类返现自动追回、退款状态表、钱包生命周期/消费批次写入、主库消费流水改造；不保证缺失日志场景的历史区间消费可自动重建。
