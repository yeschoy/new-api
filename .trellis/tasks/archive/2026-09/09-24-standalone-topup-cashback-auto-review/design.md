# 技术设计：独立充值返现、分级审核和逐场活动

> **退款设计范围**：仅管理员只读的区间已记录消费、最终 FIFO 剩余和参考金额；给付、钱包及返现处置由管理员手工完成。旧四张退款确认/生命周期侧表、两列 CNY 确认绑定与退款确认提案已取消；仅一张有序入账侧表经用户追加批准。用户允许区间消费为已记录参考值，并明确由管理员在查询前确保相关业务已结算，报表假设钱包余额为最终值，不新增在途生命周期证明；最终批次剩余仍以完整有序入账、可解释变动为前提独立计算，不把日志完整性作为必要条件。活动和易支付验签证据不受影响。

## 1. 边界与既有合同

保留现有 `TopUp -> CashbackOrderContext -> CashbackReward -> cashback_settlement -> User.quota` 的主数据库事务链，仍只接已验签的在线支付成功路径。既有 `inviter` 与 `invitee` 枚举/API 值不改名：对外将后者展示为“充值人返现”，避免改写已存记录。邀请人方向的有效关系及人工审核保持；充值人方向不再依赖 `InviterId`。首次启用前订单不补发，已生成旧奖励可继续结算。

活动只约束充值人方向；`inviter_enabled` / `inviter_rate_bps` 仍是独立方向配置。`invitee_enabled` / `invitee_rate_bps` 仍为充值人方向总开关/比例，必须同时满足总开关与活动有效期才产生充值奖励。活动结束或次数用尽不抑制合格邀请人奖励。设置界面解释总开关与活动状态的区别，避免一个开关偷偷创建没有期限的活动。

## 2. 持久化与兼容

新增独立 `CashbackCampaign` 侧表（主库），保存 `id`、`start_at`、`end_at`、`stopped_at`、`max_rewards_per_user`、`created_by`、`stopped_by`、`created_at` 等审计字段。时间一律 Unix 秒，半开区间 `[start_at,end_at)`；提前结束后的有效上界为 `min(end_at,stopped_at)`。起止时间与上限在创建后不可改；无进行中/已安排活动的重叠区间。使用稳定的配置版本 Option 行串行化创建和提前结束操作，并在主库事务内检验重叠；校验当前/未来时间与正数上限，服务端自行判定状态（计划中、进行中、结束），不信任客户端时钟。

为 `CashbackOrderContext` 添加兼容旧行的 `campaign_id=0`：下单事务根据服务端当前时间/活动区间和总开关捕获活动归属，无活动即 0，不能在支付时补选新活动。`CashbackReward` 通过已有 `top_up_id` 关联订单上下文获取活动 ID，不重复添加活动列；仅新增可区分自动/管理员/历史审核来源的 `review_source`，活动筛选按上下文与奖励既有唯一 `top_up_id` 索引联查。旧订单/奖励保持无活动且可继续处置，不强制回填、删除或改写。旧审核来源为空时按已有 `reviewed_by` 推断展示而不回写历史。活动自身为历史证据，已生成奖励仍由既有配置/风险快照决定金额、审核与到期。MySQL 5.7.8、PostgreSQL 9.6、SQLite 不使用不兼容的部分索引、JSON 列或方言专用锁。

配置仍在 `cashback_setting.*` Option 命名空间增加仅充值方向的 `auto_review_enabled`、四档 `*_review_required` 及 `auto_review_immediate_issue`；主开关默认 false，低/中档默认为 false，高/严重档默认为 true，立即发放开关默认为 true（主开关关闭或对应风险档需人工时不生效）。配置 GET 返回实际值；旧客户端 PUT 缺少新字段时必须在同一锁定的更新事务内沿用当前值，不能把高/严重默认策略悄悄重置。既有字段仍按原完整替换校验，`first_enabled_at` 和版本继续由服务端管理；活动创建不把旧全局首次启用时间改写为每场时间。

## 3. 活动资格与计次

`InsertOnlineTopUp` 的同一事务写入活动 ID 和原有下单资格快照：只有下单时处于活动有效时间、充值总开关开启且已达到既有首次启用边界才绑定；同秒启用的顺序以已提交事务中活动的可见性/绑定结果为准。`CompleteTopUpCashbackTx` 在原支付事务内根据绑定活动 ID 读取/锁定活动，确认支付成功时间也在该活动有效区间、未提前结束且支付时充值总开关仍开启。付款后才创建的活动不能认领旧订单；活动结束后旧订单只完成普通充值，不生成充值方向奖励。邀请人方向按原首次启用、支付来源和关系规则独立判定。

先按方向筛选合格受益人，再沿现有 `lockCashbackUsersTx` 的升序用户锁，对每个受益人计算滚动 24 小时额度；充值方向同一用户锁内查询本活动中 `reward_quota>0` 的充值奖励数量，对照活动正数上限后才写奖励。零额保留为可解释的 `canceled` 记录、不消耗次数；次数已满则不创建新充值奖励，邀请人奖励可继续创建。已占次数的奖励即使后来被拒绝、取消、追回或退款，也以初次正额 `reward_quota` 持续计数。现有 `(top_up_id,direction)` 唯一索引及支付事务幂等保护重复回调；三方数据库下对并发订单测试锁序与封顶。

## 4. 风控与审核状态

`CashbackReward.validate` 按方向校验关系：邀请人奖励必须有有效、非自邀关系；充值人奖励允许 `inviter_id=0`，受益人必须是订单充值人，若有邀请人只作为可用风险证据。`cashbackHardBlockReasonTx` 对充值方向重查订单、充值人账号、完成来源、异常与欠额，但不因邀请人变化/失效阻断；邀请人方向保留完整原硬阻断。风险快照中邀请人聚集/关系年龄仅在有有效邀请人时计算，不将缺失邀请人误判为风险；IP/设备/支付/金额等信号仍覆盖充值方向。管理员列表、风险筛选和汇总持续展示高/严重风险（包括自动批准的记录）。

奖励创建时按支付时保存的配置和风险等级判定 `pending` 或 `approved`：仅充值方向且主开关开启、该等级无需人工审核时自动批准，写入 `review_source=automatic`、审核时间，保持 `reviewed_by=0`（与管理员 `review_source=manual`、`reviewed_by>0` 区分，不伪造管理员审计）。邀请人始终 `pending`。若自动批准且立即发放开关开启，单独将该奖励的 `available_at` 设为支付成功时间，并在同一经验证的支付成功事务中，在复核对账/硬阻断/额度、获得充值用户额度 fence 的前提下写主额度与唯一资金 mutation；T+N 不约束这一条奖励。开关关闭时虽自动批准但 `available_at` 仍为支付成功时间 + T+N；手工审核的两方向一律保留 T+N。后续配置变更或活动关闭不追溯改变已生成奖励状态和到期时间。

立即路径不可在支付事务内调用会开启另一事务的 `IssueCashbackReward` 或用未受 fence 保护的 DB/缓存调用；应将现有发行检查/额度 mutation 抽取为能在已有支付事务和已持有的付款人额度 fence 下复用的事务内逻辑，使用事务本身执行有界对账检查（避免对全局 `DB` 做嵌套查询导致 SQLite 单连接死锁）。五个支付渠道共同通过 `CompleteTopUpCashbackTx` 到达该逻辑，正常充值主额度及返现发放均应同提交/同回滚；若对账、Redis fence 或发放校验失败，则本次支付完成事务失败并交由已验证支付回调重试，不承诺绕过检查的即时入账。发放记录的尽力日志在提交后记录，不作为资金证据；主库唯一 mutation 和状态保证重复回调不会二次发放。

## 5. API / 管理端

Root 配置 GET/PUT 沿用原路由，新增审核策略与免审后立即发放字段，服务端校验并把变更字段纳入审计；前端明确说明仅自动批准的充值奖励适用该开关，关闭开关仍有 T+N。本次只读报表不新增商户 CNY 收款确认设置：易支付签名金额不包含币种，管理员必须在本次报表查询显式确认商户实际收款为 CNY，才能按签名分展示**管理员确认下的参考金额**；确认不持久化为支付币种事实，不能标为系统已核实。活动采用 Root 权限的 `GET /api/cashback/campaigns`、`POST /api/cashback/campaigns`、`POST /api/cashback/campaigns/:id/stop`，创建/结束含稳定审计 action、权限与限流、时间与上限校验、并发创建防重叠；早停幂等，已结束活动不可重启或修改。活动列表可见开始/结束/早停时间、次数上限及创建人，返现详情可追溯关联的活动 ID；既有 Admin 奖励列表保持风险筛选，可按活动 ID 补充过滤。

复用现有 Root `CashbackSettingsForm` 与其 SettingsSwitch/Form 组合、已有输入与确认组件，在同一区域增加分级审核策略和活动创建/列表/提前结束；复用 Admin `/cashback` 的现有风险过滤、表格与详情，调整方向文案、显示关联活动/自动审核来源。只读退款区域按充值节点展示日志所记录的区间消费合计、购买/赠送推算余额与参考额；缺完整资金来源或仅有未经核实的币种时，显示人工核对提示而非准确现金总额。没有确认、付款或返现追回按钮。i18n 用既有七个 locale 文件和项目翻译流程；不新增平行的第三方向或重复造表单/对话框。校验、完整配置替换及 API 类型在前后端同步。

## 6. 兼容、发布与回滚

活动和易支付证据侧表及两处返现列需纳入常规/快速 AutoMigrate，验证新库和最新发布版 `v1.0.0-rc.40` 的代表数据升级并重复迁移；若该发布版还没有返现侧表，也须测试当前分支旧返现数据的升级兼容。活动表只有新记录，旧 `campaign_id=0` 允许继续审核、到期结算与退款处置。新安装和升级均不自动造无限期活动；用户表示目前活动未开始，但线上现状尚未直接核实，发布前应检查实际开关与奖励数据。若发现实际正在进行的活动，需回到产品决策而非静默截断。

异常停用新计提：关闭充值总开关或提前结束当前活动；关闭只影响后续支付，已经生成的返现仍按快照处置。生产代码回滚前需评估已即时发放奖励：它们已混入可消费的主额度，不能靠回滚代码撤销；旧版不会识别活动上限，故应先停新订单计提。不得通过删除表或人工改余额回滚。

## 7. 只读充值区间与退款参考报表

**实施边界**：当前工作区已新增 `cashback_campaigns`、`epay_payment_evidences`、`admin_quota_credit_evidences` 三张主库侧表，以及 `cashback_order_contexts.campaign_id`、`cashback_rewards.review_source` 两列，仍须三库迁移校验。用户追加批准下述**仅一张**低频 `wallet_refund_credit_events` 主库侧表；不新增退款确认/生命周期表、钱包消费记录、CNY 确认绑定列，`User`/`TopUp` 不加列，普通 API 消费不写此表。旧 `research/refund-schema-blockers-resolution.md` 仅保留为已撤销的历史方案，不作为实施清单。

**新表完整清单/开口**：`wallet_refund_credit_events`：`id` bigint 自增主键；`user_id` bigint 非空，索引 `(user_id,id)`；`event_key` char(64) 非空、唯一（业务来源幂等键的摘要，避免存明文兑换码/密钥）；`kind` varchar(24) 非空（`opening`/`purchase`/`gift`/`nonrefundable`/`exception`）；`source_type` varchar(24) 非空，`source_id` bigint 非空默认 0；`quota` bigint 非空（入账正数、opening 可为零，exception 为零）；`created_at` bigint 非空。无其它索引或现有表新增列。来源本身的金额/币种沿现有 `EpayPaymentEvidence` / `AdminQuotaCreditEvidence` 读取，不在此表复制现金金额。所有该用户事件**先获得同一钱包用户行/数据库事务串行点后**插入，ID 而非秒级时间决定其真实入账顺序。新用户初始钱包额同注册事务写 `opening`，作为不可退首段；存量用户只有在管理员已确认历史操作结清、全部实例均运行新写入代码后，于首次被覆盖的低频入账事务中将变动前余额写成不可退 `opening`，再写当前入账。旧记录不回填成可退批次，首次开口前旧订单一律人工核对；一旦发生异常或来源不明、仍有旧实例可能绕开证据写入，报告仅人工核对。部署变量 `CASHBACK_REFUND_REFERENCE_ENABLED` 默认关闭数字报价（仍允许读已记录消费）；确认新写入路径覆盖所有实例、旧混合余额/线下给付由管理员核对后才设置为 `true`，并只对有安全开口、无异常的用户报价。应用回滚前关闭数字报价并保留证据表/已产生行，不用旧应用在证据缺失时继续报价。

**低频写入路径/金额边界**：已验签在线充值及人工补单的实际购买入账与对应事件同事务（人工补单额度占 FIFO 但无验签 CNY 现金凭据）；即时赠送排在同笔购买之后，延期赠送在实际发行事务按受益人入队（邀请人赠额只入邀请人钱包）；额度兑换码仅写 `nonrefundable`，套餐兑换不写钱包事件；注册初始额作为 opening、签到/邀请额度转入写不可退事件，管理员 add 复用既有 `AdminQuotaCreditEvidence` 的主键/面额并新增对应有序购买事件。管理员 subtract/override、现金事故/来源指定追回只写 `exception`（零额度标记，不能被当普通 FIFO 消费），其后该用户暂停自动金额；未知来源的直接钱包变动也必须标异常而非静默略过。`opening`/`exception` 仅保守拒报，不用负数事件虚构购买余额；若实际入口无法以原钱包更新的同一主库事务写证据，则该入口用户人工核对，不假称全覆盖。唯一来源键和现有订单/奖励幂等性一起保证回调重试不重复入队。不能为了证据改变原有的充值、赠送、兑换或管理加额数值。

**迁移/发布/回滚**：正常及快速主库迁移注册新表；SQLite、MySQL≥5.7.8、PostgreSQL≥9.6 的新建与真实发布代表数据升级均重复迁移两次，核查旧余额/订单/码保持、唯一键和用户事件顺序；涉及的 LOG_DB 路径另行确认但不把日志当证据。老用户不自动补历史购买，只在安全开口后未来入账有资格参考；老代码混跑、缺证据、异常和已线下退款均转管理员人工。三库未实测前不称数据库兼容，不删表回滚。
**只读计算路径有两条、不可混同**：主库余额、入账事件和来源在同一个 Repeatable Read 只读快照中读取，`LOG_DB` 在事务结束后独立查询，避免 SQLite 单连接死锁。① 区间展示按充值支付完成节点查询 `LOG_DB` 中**已记录**的消费总额，另列可识别的订阅等扣款；不因总账对齐就称它涵盖全部支出，也不展示逐次 API 消费。② 最终额度计算独立于日志：取得可信已结清的钱包余额 `Q`，按实际到账顺序列出全部可核实额度段 `G`（旧混合余额不自动列为可退；其他渠道与管理员 `add` 入账作为有序购买额度段（管理员批次按入账时声明的 CNY 面额作现金参考）；额度兑换码（`plan_id=0`）、注册等赠额为不可退款段；订阅套餐兑换码（`plan_id>0`）不触碰钱包；同单购买先于即时赠送；迟发赠送在实际发行时追加）。若所有非入账变化均可归为已结清普通净消费、无来源指定冲正/未知调整，则 `S=sum(G)-Q` 为总净消耗，从最旧段的购买→当时可用赠送→后续段顺序消耗 `S`；逐单剩余购买额度与区间日志是否完整无关。其他变动无法解释或入账顺序不明时不输出准确金额。现金按可核实易支付实付比例换算，赠送额度不计。查询不改状态；已线下退款/追回须由管理员另行核对。

**净额与节点边界**：普通 API 预扣及退还只在已结清后按最终净消耗归属；旧购100预扣100→新购50→再消费40→旧预扣退还100，最终参考旧购余60、新购余50。尚在预扣/异步退还时不能以余额算最终消耗。真实迟发赠送只从实际到账参与；旧购100→新购50→消费105→旧单赠10到账，参考新购剩45。既有模型并无跨实例持久的请求结清证明；本报表按管理员负责确认已结算的业务假设运行，不声称系统验证了这一事实，假设不成立时参考值会失准。

**可观测性而非资金证明**：`RecordConsumeLog` 可被关闭且失败不回滚扣费，日志位于可独立配置的 `LOG_DB`；订阅余额支付和管理调整并非普通 API 消费日志，批量额度还可能只在内存中待刷。因此按区间 `SUM(Log.quota)` 只能称为「已记录消费」，不是实际发生的区间消费。相同总净消费可发生在两次充值之间或之后：最终钱包余额不能倒推出**区间**分布；但在全部额度入账有序且其余变化只是普通 FIFO 净消费时，最终各段剩余是余额对应的入账后缀，不受普通消费发生在哪个区间影响。**只缺消费日志**不阻断独立的最终余额推算；缺真实入账、特殊扣减证据、旧余额归属或仍在途预扣才使最终金额不可信。

**货币换算**：逐单以签名实付整数分 × 推算未消耗购买额度 ÷ 原购买入账额度向下取整，上限为该单签名实付分；不把赠送额度、面值或 `TopUp.Money` 当实付。不为其他通道换汇。当前 `EpayPaymentEvidence` 保留验签金额但 Epay 协议不签币种；管理员 `AdjustUserQuota(add)` 只接收内部额度，前端按当时展示币种/汇率转换输入金额，既未在额度事务内冻结原始 CNY 面额，也没有支付凭据；用户最终澄清“调整的金额是多少就是多少”：不改变原表单的 `parseQuotaFromDollars` 加额额度计算。表单确实显示 CNY 时把管理员原始输入解析为正整数人民币分，随原 `value` 发送；服务端将 CNY 分视作管理员声明的业务面额（不是支付凭据），校验边界后同一事务保存这笔原有额度和原输入分。显示 USD/token/其它币种及旧客户端不提供 CNY 分，留证 `NULL`；旧批次不能从今日额度单位/汇率倒推。即使按业务约定报价，也只能称人工给付参考而不能声称验签实付；不新增持久 CNY 确认时，系统不能自己证明人民币实收，即使管理员知道商户收 CNY 也只能将换算值标为待人工核对的参考，不能自动给出「已核实 CNY 可退总额」。

若可观察的入账/特殊扣减与钱包净变化无法解释，隐藏已核实现金总额并展示「需人工核对」，而非调节某个区间使余额对齐。即使总数一致，区间仍标注日志统计的局限；普通 API 消费日志缺失本身不等于余额证明失效。存在来源指定追回、其他渠道购买、额度码兑换/签到/管理员正向加额时，需核实其到账时间和额度才能参与最终 FIFO，其中额度码只作不可退批次；套餐码兑现只生成订阅权益、用套餐额度的 API 调用不计钱包消费；钱包余额购买套餐则是钱包支出；`add` 算可退购买额度段而非自动忽略，`subtract/override` 属特殊变动。管理员批次已确认可按 1:1 CNY 折算参考退款，但现有额度值不能反推输入时的 CNY 数字；旧批次缺当时人民币面额时转人工，不以当前可变汇率补造历史；新批次的持久方案须先过数据库变更确认门禁。证据不足只给人工核对提示。历史混合余额、已在外部退款订单同样由管理员核对。

**接口与风控**：只读 Admin 查询，按用户/充值节点分页或限定时间与订单数量；分别返回 `recorded_interval_spend`（日志参考，不参与最终 FIFO）、购买/赠送推算余额（仅资金证据充分时）、支付凭据状态、人工核对原因及可展示的参考金额，明确计算时间与数据来源。不得提供退款确认、额度扣回、记录给付状态的 POST；同一用户重复查看不改变钱包或返现。查询的访问控制与敏感信息审计遵循现有 Admin 规则。若产品未来要求系统保证完整区间和准确可退金额，需要另立经确认的资金证据设计，不能在此只读报表中隐性加入逐次消费持久写入。

活动仍需要独立 `CashbackCampaign` 持久化；只在已有 `CashbackOrderContext` 保存一处订单活动 ID，奖励通过订单联查，不改核心 `User` / `TopUp` / 消费日志表。已写的 `EpayPaymentEvidence` 属于支付验签金额留证，不代表商户 CNY 确认或完整消费流水。

### 管理员 `add` 人民币面额：已确认的有界结构（额度证据已部分实施）

用户在确认“普通每笔消费不新增写入、仅管理员正向入账写证据”后要求开始。审批只覆盖下列一张主库侧表，不等于批准历史补造、全钱包自动报价或新增其它表。当前已实现每次 `add` 在余额主库事务内写入唯一额度证据，`cny_cents` 一律 NULL；下一步仅针对新版明确的 CNY 加额输入补齐面额。用户澄清无需区分“新老换算模式”：保留既有 `add` 页面及 `parseQuotaFromDollars` 的额度计算/预览，消除当前未提交实现默认改为固定 CNY→额度 1:1 所带来的行为变化。仅在页面展示币种为 CNY 时解析**管理员输入的人民币金额**（正值、最多两位小数）成 `cny_cents`，随现有 `value` 传给服务器；服务端只校验 CNY 分及额度各自边界，不基于可变汇率重新计算或替换 `value`，把本次管理员声明面额与实际入账额度同事务保存。USD/token/其它币种与旧客户端仍按旧逻辑加额、CNY 面额保持 NULL；日志和报表不得将管理员声明说成已验签收款或完整退款报价。无需改 Option 写路径，也不从当前配置回填历史。

现有未提交的主库结构仍为 `cashback_campaigns`、`epay_payment_evidences` 两表及 `cashback_order_contexts.campaign_id`、`cashback_rewards.review_source` 两列；它们分别服务活动与验签，不记录管理员加额输入。当前 `AdjustUserQuota(add)` 只将内部额度写入 `User.quota`，管理员操作审计与充值日志在提交后尽力写入 `LOG_DB`；它们不能作为事务内的历史 CNY 面额证据。

针对**仅保存新发生的管理员正向加额**，候选为新增一张主库 `admin_quota_credit_evidences`，不改 `User`、`TopUp` 或消费日志的表结构：`id` 自增主键，`event_key` char(64) 全局唯一，`user_id`、`operator_id`、`credited_quota` bigint、`cny_cents` 可空 bigint、`credited_at` bigint，并建 `(user_id,id)` 查询索引。`credited_quota>0`，有金额时 `cny_cents>0`、币种固定 CNY；空值表示旧客户端未提供面额、该批次只能参与 FIFO 额度而不能自动报现金。每次 `add` 与该行必须在同一主库事务提交/回滚；显式 CNY 输入分须由服务端校验正值、范围与只适用于 `add`，原有 `value` 的额度安全校验维持不变。不得为了金额证据重新计算或改变 `value`，也不得把 CNY 分误作支付验签金额。`subtract/override` 不写这种购买证据，也不能用差额假扮充值。管理员人工补单 `ManualCompleteTopUp` 是另一条已有 `TopUp` 路径，不能和此表重复计入；未验签实际付款仍需人工核价。

兼容：不回填历史管理员加额，旧行没有面额时显示人工核对，不以当前汇率倒推；旧客户端仍可加额但写 `cny_cents=NULL`。新旧服务实例混跑期间不得声称证据完整。发布前在 SQLite、MySQL、PostgreSQL 对新库、代表性旧库升级、重复迁移及唯一索引验证；回滚应用前关闭基于新表的报价，保留表中证据不删。**此单表只解决管理员加额面额留证，不保证所有支付/赠送/兑换来源的跨表入账顺序或旧混合余额；预扣/批量余额是否结清由管理员负责确认，因此不能把最终金额称为系统核验后的准确退款额，也不能仅凭此表交付全部逐笔参考值。**如整体证据模型最终需一张共享有序入账表，必须重新列明字段、写入路径和迁移范围供用户确认，不默默把本候选扩成资金账本。

## 8. 权衡与验证风险

- 选新增独立活动表 + 订单/奖励活动 ID，不复用不可重置的 `first_enabled_at`，以保证多场历史、同秒订单归属和计次可审计。
- 复用 `invitee` 枚举/配置 wire 字段而在 UI 改称“充值人”，减小旧数据库/API 升级爆炸半径；若日后重命名，另立兼容迁移。
- 只在创建时自动审核，后续不批量修改旧 `pending`，避免策略切换造成历史余额突然解冻。立即发放按单笔奖励的支付时快照决定，不追溯作用于旧 `approved/frozen`。已即时发放的奖励遇退款仍走原追回/欠额路径；到账后可立即消费使追回失败形成欠额，这是及时性相对于 T+N 的真实资金风险，需在产品审阅中明确。
- 数据库变更必须通过真实 SQLite/MySQL/PostgreSQL 矩阵、升级及重复启动。当前环境 Docker 守护进程未运行、`TEST_MYSQL_DSN` / `TEST_POSTGRES_DSN` 未配置，但本地 MySQL/PostgreSQL 二进制存在；实施阶段尝试隔离实例。无法跑齐矩阵时不得宣称 DB 兼容或任务完成。
