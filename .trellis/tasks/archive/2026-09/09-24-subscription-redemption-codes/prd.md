# 订阅套餐兑换码

## Goal

管理员可发行和管理关联套餐的兑换码，用户在原有兑换入口输入后直接获得对应订阅；既有额度兑换码仍照常充值钱包。尽量复用现有兑换入口、管理页及订阅授予机制。

## Background

- 当前 `model/redemption.go` 只有额度 `Quota`；`controller/user.go` 的 `TopUp` 经 `/api/user/topup` 调用 `Redeem`，返回数值额度。
- 管理端 `controller/redemption.go` 和 `web/src/features/redemption-codes/` 仅支持额度码；钱包入口在 `web/src/features/wallet/`。
- `model/subscription.go` 的 `CreateUserSubscriptionFromPlanTx` 可在事务内创建用户订阅并执行套餐购买次数限制；余额购买检查套餐启用状态，管理员手动绑定当前不检查。
- 订阅套餐配置可能在码发行后变更；套餐可被停用。当前数据库支持 SQLite、MySQL 和 PostgreSQL，兑换码表由 `model/main.go` 的 `AutoMigrate` 维护。

## Requirements

- R1 管理后台在原兑换码管理流程中创建、查看、编辑、禁用、删除与导出额度码和套餐码；套餐码选择一个有效套餐，列表及移动端能识别权益类型和目标套餐。输入不能同时产生两种权益。
- R2 用户在原兑换入口输入额度码仍增加钱包额度，原额度码的 API 成功响应保持数值额度；输入套餐码直接获得指定套餐而不增加钱包余额，页面明确显示兑换的套餐。
- R3 套餐码关联套餐 ID，**按兑换时的最新套餐配置**授予权益，不在发码时固定权益快照（用户确认）。套餐停用时，未使用的套餐码暂停兑换且不消耗；重新启用后可兑换（用户确认）。套餐不存在、已达用户购买次数上限或授予失败时也不消耗兑换码。
- R4 兑换码仅可成功使用一次；兑换码使用记录与钱包充值或套餐开通必须原子一致，并发和重复请求不得重复授予。已使用码不得通过后台重新启用以重复兑换。
- R5 既有兑换码数据在升级后仍被识别为额度码；维持现有有效期、禁用、权限、支付合规及对外失败屏蔽行为，不依赖仅前端的校验。

## Acceptance Criteria

- [x] AC1 管理员能发行一批额度码或指定启用套餐的套餐码，管理页清楚展示两种权益、允许管理未使用的码并导出正确的权益信息；无效类型、无效套餐及错误额度被后端拒绝。
- [x] AC2 原额度码充值额度、响应中的数值及现有 UI 提示不变；旧数据迁移后仍按额度码处理。
- [x] AC3 套餐码从原入口成功兑换后用户获得一份对应订阅，UI 能显示套餐名称，钱包额度不变；套餐权益使用兑换时配置并遵守既有购买次数限制。
- [x] AC4 无效、禁用、过期、重复、并发、套餐停用/不存在和授予失败均不产生多余权益；失败后可重试的码保持未使用，停用套餐重新启用后可继续兑换。
- [x] AC5 新增列在三个数据库的新建与既有数据升级路径上迁移可重复执行，保留原有码与唯一性；受影响的后端与前端测试通过（不含在基线已失败的全量 controller 套件）。

## Out of Scope

- 发行时固定套餐配置、批量把旧码转换为套餐码、独立的第二种兑换入口、创建新的订阅付费方式、套餐删除/退款功能。

## Validation Risk

- 规划时 Docker 不可用；实施阶段已以仅 Unix socket 的隔离本地 SQLite/MySQL/PostgreSQL 实例跑通本变更的迁移与兑换事务矩阵，具体版本、命令和结果见 `research/existing-flows.md`。全量 controller 套件仍存在在本任务基线复现的 OAuth/注册/额度缓存失败，不将其误报为本任务验证通过。
