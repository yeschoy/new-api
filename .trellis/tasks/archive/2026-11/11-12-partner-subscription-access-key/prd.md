# 商户开发者密钥下单与独立订阅 Key 查询

## 状态与目标

状态：**in_progress**。用户在最终摘要（规划提交 f8aeb6a5a）之后明确答复“开始”，已批准本版实施并成功运行 task.py start。已确认：不传 external_user_id，可信付款后才新增真实内部用户，原订阅 Key 定位续费；仅必要 PostgreSQL 验证。原 Docker/模块缓存阻塞及代理超时历史保留；经限定恢复，任务专属 PostgreSQL 定向运行已首次通过（详见 verification.md），不替代完整启动、生产迁移/真实支付/部署；后续独立审阅已完成且无本范围业务阻断，也未以宿主测试或其他数据库替代。

原始目标是新增一种商户接入方式：商户用开发者密钥创建订阅订单，买家付款后由商户交付独立订阅 Key。买家无需商户秘密即可查询自己购买的订阅、额度及真正的 Coding API Key，而不需要注册或登录平台。

## 仓库背景与证据

以下仅为当前分支源码事实，不表示现有功能已上线或支付/数据库运行验收通过；详细历史取证及决策记录保留在 research.md。

- `middleware/partner_tenant.go:15`、`controller/partner_tenant_order.go:160`、`model/partner_tenant_order.go:119`：已有 pt_ 鉴权与付费订单，但旧入口强制 external_user_id，不能直接套用于新方式。
- `model/partner_tenant_order.go:361`、`:375`：可信 paid 之后才在交付事务开户、授予并记录 SubscriptionId；支付事实独立提交，本地失败可恢复。
- `controller/partner_tenant_order.go:250`、`:279`：现有商户查单/公共收银台均不返回调用凭证；pc_ 是短期订单访问权，不能扩大为长期取钥权。
- `model/partner_tenant.go:45`、`:255`、`:392`：旧映射按商户外部用户维护 UserId/TokenId，可有多份订阅；授予核心可通过冻结续费 ID 复用原订阅。该外部身份关系不是新方式的要求。
- `controller/partner_tenant.go:162`、`model/subscription.go:908`：旧额度接口查询账户下全部有效商户订阅，且包含周期重置，不能作为新 Key 的授权范围。
- `controller/partner_tenant.go:83`、`model/partner_tenant.go:169`：现有重置是商户开发者密钥重置，不是订阅 Key 重置。
- `web/src/features/subscriptions/components/subscriptions-mutate-drawer.tsx:355`、`controller/subscription.go:150`、`:319`：root 已有商户专属套餐配置入口及归属不可变校验；`controller/partner_tenant.go:223`、`model/partner_tenant_order.go:113` 已按商户限制目录与下单。
- `model/partner_tenant_order.go:436`、`:448`：外部身份查询及历史哈希回填是显式隔离内部身份时必须处理的兼容边界。
- 支付/H5 既有安全合同分别见 `.trellis/spec/backend/partner-tenant-checkout.md`、`partner-hosted-h5.md`；迁移遵守 database-guidelines.md。

## 已确认需求

| ID | 要求 |
| --- | --- |
| R1 | 新增商户开发者密钥鉴权的无终端用户 ID 下单方式。创建/续费下单返回 order_no 与 checkout_url，链接进入现有平台收银台；初始响应不返回订阅 Key 或 Coding API Key，保留旧接入契约。 |
| R2 | 付款且本地交付完成后签发独立订阅 Key，与开发者密钥和 Coding API Key 的秘密值、用途不同。 |
| R3 | 独立查询接口仅需订阅 Key，不要求商户开发者密钥、商户 ID、商户登录或平台 Cookie；返回关联的单份订阅信息、实时额度和可用 Coding API Key，终态见 R9。 |
| R4 | 订阅 Key 不能调用 Coding，也不能通过参数扩权访问同账户其他订阅或其他用户数据。 |
| R5 | 仅可信支付确认并完成交付才可领取；浏览器回跳/客户端 paid 声明不能开户授权。重复通知和交付恢复不重复开户、授予或签发。 |
| R6 | 订阅 Key 可读取 Coding API Key，必须作为秘密处理，不进入 URL、日志、公共缓存或无关响应；额度输出不得损失 int64 精度。 |
| R7 | 商户后端以开发者密钥领取其已交付订单的订阅 Key，再按自己保存的订单/购买意图交付。平台不要求买家 ID，公共收银台及 H5 不展示或返回长期凭证。 |
| R8 | 已确认续费通过原订阅 Key 下单定位原订阅，商户仍用开发者密钥鉴权；付款后复用原用户、原订阅、Coding API Key 和订阅 Key。不带续费目标是独立新购，不按商户+套餐推断买家，不合并不同订阅或把原 Key 改绑新订阅。 |
| R9 | 自然到期后原订阅 Key 可读该订阅的到期状态和历史额度，但不返回 Coding API Key；历史余额不表示当前可消费权益。 |
| R10 | 本期提供仅商户后端可调用的订阅 Key 重置；新 Key 生效后旧 Key 的后续请求失效，不改变 Coding API Key 或权益。 |
| R11 | 套餐配置采用 A：每商户可配置多份专属套餐，一份仅归一个商户。复用 root 既有配置入口；目录和新下单只允许当前商户名下已启用套餐，不能伪造 plan_id 绕过，不新增共享授权。 |
| R12 | 商户新接入不传 external_user_id 或其他买家身份，不要求先开户/登录或伪造用户 ID。平台维护内部关联，幂等键仅表示一次购买意图。 |
| R13 | 用户选择 A：首次新购仅在可信付款成功后的完整交付中新增真实 users 记录。创建订单/返回付款 URL、未付、支付失败/未付超时不开户；后续可信迟付仍按已付交付。交付失败不留下部分用户/凭证/权益，paid 独立保留以便恢复；续费及同订单重试不重复新增。 |

## 范围及兼容边界

- 包含服务端新购/续费、商户查单/领取、独立查询、商户重置、增量迁移、接入文档、安全规范及必要验证；专属套餐复用现有后台，不新增买家页面、重复管理页面或商户 webhook。
- 旧 external_user_id API 和可选托管 H5 保持各自身份及 DTO 契约，不迁移/改绑旧账户，不给旧模式的历史或未来订单自动签发新 Key，不靠 GET 补发、开户或授予。
- 新方式的每份独立新购建立独立内部 User/Token/订阅关系，不借用商户共享用户、用户 0/负数，也不让旧外部身份接口命中新内部账户。正常续费不换两种 Key、不新增用户。
- 本期只做同套餐续费，不增加跨套餐换购/升级、跨订阅合并、钱包充值、自动退款或 Coding API Key 轮换。价格、额度单位、支付渠道及普通用户鉴权/计费/RPM 算法不变。续期沿用月度周期语义，不因延长有效期立即额外叠加当期额度。
- 用户选择新增真实内部 User，放弃无 users 独立主体改造；原可行性评估仅保留为 Trellis 研究记录。
- 重置只撤销旧订阅 Key 后续用途，不能撤回已获得的 Coding API Key、已授权请求或已发出的响应；不增加根秘密轮换/KMS、独立撤销系统。
- 不包含生产访问/部署、真实付款、私钥读取、既有测试数据删除或未经同意的资源清理。

## 验证与交付限制

- 用户明确“只做有必要的测试”，且“不需要验证sqllite，只需要验证pq”。只跑本功能生命周期、鉴权/精度/敏感 DTO、直接受影响的支付交付及 PostgreSQL 迁移/关键并发，不跑全站、无关前端或计费套件。
- 数据库仅验证隔离 PostgreSQL，不运行 SQLite/MySQL/FoundRows/完整旧订单矩阵。必要 HTTP fixture 不调用会隐式初始化 SQLite 的旧 setup；保留原跨驱动代码支持。
- Go runner 和数据库均用本任务专属 Docker。迁移/持久化需真实 pq 证据，build/vet 不替代 runtime；报告未验证项与环境阻塞，不把无关全量测试未执行列为新增阻塞。
- 代码、文档及相关 Trellis 文件按明确范围提交 Git，不覆盖既有 docs/partner-tenant-integration.zh-CN.md 修改，不暂存私钥，不 push/部署；npm/pnpm 缓存及诊断记录保持 Git 忽略。
